### Codex/GPT 工作流启发

1. iOS 端“打开即进 Codex Remote”说明手机正从提醒器变成控制面，但它仍不应成为完成证据来源。移动端适合 steer，不适合 final accept。
2. 标准 MCP 表单和可编辑 message approvals 让移动审批更像结构化审批单。审批前要看到动作、对象、影响范围和可撤销性，不能只看到一句自然语言。
3. Voice 直接接入 task composer，适合把临时想法转成 steering message；但语音输入要有取消/编辑和发送前确认，避免口误直接改变执行方向。
4. Codex CLI `/export` 把长会话换车从人工摘要推进到可复制 artifact。对高价值任务，导出 Markdown 应成为 handoff 的默认候选。
5. `codex exec fork` 和 TUI archive/restore 让探索分支变得便宜。规则是: 可以分叉探索，但最终写入 owner 只能有一个，避免多个分支同时改同一文件。
6. `/status`、status line 和 terminal title 的 thread cost/credit 让“感觉很贵”变成可记录指标。日报、研究和修复任务都应有预算档位。
7. async hooks 和 MCP tool hooks 说明 Codex 的可编排性在增强。确定性检查应该放进 hook/runbook，而不是靠最后人工回忆。
8. Bedrock Runtime provider 支持提醒我们: provider 越多，越要记录模型、region、auth、sandbox、数据边界和不可外发内容。
9. GitHub reasoning level for cloud agent 与 Codex thread cost 是同一类信号: 任务启动时应同时选模型和推理档位，而不是默认开最贵档。
10. comment-triggered automation 很方便，也会让“能评论的人”间接触发 agent 花费和工具动作。触发词、仓库可见性、工具范围和审批门要一起设计。
11. MCP allowlist/denylist 证明 MCP 治理不能只靠用户自觉。白名单要匹配 remote URL、本地 command 和 baseline 策略，且 malformed config 应 fail closed。
12. managed settings team specialization 提供了团队级治理模型: 中央策略定底线，团队只在被允许的字段上扩展。
13. code review effort levels 把审查强度变成显式选择。小改走 Lite，大改、跨服务、安全相关走 Balanced；本地自动化也应有“轻审/深审”两档。
14. agent app usage metrics 把多 agent 选择从偏好变成数据问题。个人也可以记录每个 agent 的接受率、返工率和适用任务类型。

### iPhone + Mac + Codex 协作玩法

今日推荐链路:

1. iPhone/Remote: 用固定模板发起任务，包含目标、是否允许发布、触发词和停止条件。
2. Voice: 只把临时想法写成可编辑 steering draft，不直接改变已进入验证/发布阶段的任务。
3. Chat: 把口语输入整理成任务胶囊，冻结读写边界、预算档位、source priority 和验收标准。
4. Luna/只读侧车: 扫描公开候选源，只回传 JSONL，不写文件、不发布。
5. Mac/Codex CLI: 执行文件写入、检查、diff、commit、push、deploy；必要时用 `/export` 生成 handoff。
6. Hooks: 把 JSONL 字段、report-data 同步、公开边界、secret scan、git diff check 做成发布前闸门。
7. MCP: 新工具先进入白名单草案，确认 URL/command、读写动作、owner 和撤销路径后再上架。
8. Metrics: 记录模型/推理档位、运行时间、sourceCards、signals、knowledgeCards、是否一次通过。

### 可沉淀知识卡片

#### 卡片 1: Mobile Steering Contract

- 概念: iPhone/Remote 是控制面，不是交付面。它可以发起、转向、审批、查看状态，但不能单独宣布任务完成。
- 操作步骤:
  1. 发起任务时写清目标、允许动作、禁止动作和是否允许发布。
  2. steering message 进入执行前允许编辑或取消。
  3. 验证/commit/deploy 阶段只允许补充检查，不直接改目标。
  4. 每次移动审批都记录对象、动作、影响范围和可撤销性。
  5. 最终完成只看 Mac/Codex 的文件、测试、GitHub 和 Vercel 证据。
- 风险: 手机越顺手，越容易把“我看见状态”误认为“我完成验收”。

#### 卡片 2: Session Export/Fork Ledger

- 概念: `/export` 和 fork 让长会话换车、分支探索和回放更稳，但需要记录源会话、分叉原因、恢复点和最终接受分支。
- 操作步骤:
  1. 长任务结束或换车前导出 Markdown 交接摘要。
  2. 分叉前写清要探索的问题和不允许改的对象。
  3. archive/restore 时记录恢复原因和预期状态。
  4. 合并结果前只接受一个写入 owner 的产物。
  5. 结束时记录被接受分支、被拒绝分支和原因。
- 风险: 分叉便宜会诱导多线乱写；没有 ledger 会丢失哪条线才是最终证据。

#### 卡片 3: Hooked MCP Runbook

- 概念: hooks 可以把自然语言 agent 流程变成可拦截流程；MCP tool hooks 则要求每个工具都有上架、审批、超时和失败策略。
- 操作步骤:
  1. 把发布前检查拆成 pre-write、pre-publish、post-deploy 三类 hook。
  2. 为每个 MCP 写 URL/command/name 三类匹配字段。
  3. 高风险写动作默认 always ask 或 safe output。
  4. hook 失败时 fail closed，并输出可读停止原因。
  5. 定期清理不用的 MCP 和 hook。
- 风险: hook 本身也可能误伤或放行；它是闸门，不是最终验收。

#### 卡片 4: Cost/Reasoning Budget Sheet

- 概念: agent 任务需要在启动时选择推理档位，并在结束时记录成本/credits、耗时、接受率和返工原因。
- 操作步骤:
  1. 按任务风险选 low/medium/high/max 档位。
  2. 记录使用的模型、provider、reasoning level 和工具面。
  3. 结束时记录 elapsed、tokens/credits/cost 可得值、产物和验证结果。
  4. 对失败任务记录失败阶段和是否重试。
  5. 每周回看哪些任务适合低档，哪些必须深审。
- 风险: 没有成本表，团队会用感觉讨论 agent 价值；没有验收表，低成本也可能只是低质量。

## 白话版

今天这期像是把施工队升级成了“手机对讲机 + 施工日志 + 分支施工图 + 电表 + 门禁系统”。

手机现在更好用了: 可以一打开就进 Codex Remote，可以审批表单，可以用语音继续派活。但手机还是对讲机，不是验收台。真正交付还得回到 Mac/Codex，看文件、测试、commit、push、deploy。

Codex CLI 0.148.0 像给施工队加了几样硬工具: `/export` 是把当天施工记录打印出来，方便换车；fork 是开一条支线试方案；archive/restore 是把现场状态收纳和恢复；cost/status 是电表，告诉你这次干活大概用了多少电；hooks 和 MCP hooks 像门口闸机，哪些动作能过、哪些要审批。

GitHub 那边的信号也一样: comment 可以叫醒 agent，reasoning level 可以调“思考用力程度”，MCP allowlist 是超市上架清单，review effort 是轻审/深审两档，usage metrics 是账本。

所以今天的结论很直白: agent 不只是“会干活的人”，正在变成“有对讲机、有账本、有门禁、有分叉施工图的工作系统”。下一步要沉淀的不是更多 prompt，而是调度合同、交接账本、工具闸门和成本表。

### Codex/GPT 工作流启发

1. Codex alpha 只有版本号和占位正文时，只能证明发布节奏，不能证明功能、修复或稳定性。
2. 稳定版没有更新也是结果；不要为填满日报把 prerelease 升格成生产建议。
3. Copilot CLI 1.0.83-4/-5 仍是 prerelease；MCP OAuth CIMD、恢复策略和 localhost sandbox 变化都要和稳定版分 lane 验收。
4. OpenAI Node SDK 7.9.0 的 usage API 与 WebSocket 修复适合做集成回归，不等于需要立即升级到最新版本。
5. 退役模型清单应包含 model key、截止日、替代模型、使用入口、owner、迁移状态和回归证据。
6. 替代模型出现在公告里，不代表组织 policy 已启用，也不代表每个客户端同步 rollout。
7. 企业默认模型与团队 override 是两层配置；最终验收仍要读回 app/CLI/VS Code 的实际模型。
8. 默认策略、model picker 和一次会话实际使用的模型可能不一致，三者必须分开记录。
9. 内容排除只是输入边界；执行后仍需扫描输出、diff、日志和发布产物，避免私有信息侧漏。
10. Claude Fable 5.1 的默认 retention 要求提醒: 模型选择表必须包含数据保留模式，不只看能力和价格。
11. 临时模型试验使用带 `expires_at` 的预算，避免一次试验变成永久额度。
12. AI review assessment、review comment、formal approval 与 merge rule 都是不同状态，不能压成一个“已审”。
13. reusable workflow 的调用方 SHA 不等于实际运行来源；要保存 `job.workflow_ref`、`job.workflow_sha`、repository 和 file path。
14. runner deprecation API 应进入 CI 预检，避免基础设施到期伪装成应用失败。
15. `vulnerability-alerts: read` 说明 agent 读安全告警时可以拆出更小的 token 权限。
16. CodeQL 新增 mutable reusable workflow 检测后，跨仓 workflow 默认使用 immutable SHA。
17. npm 多 OIDC 配置是 additive；任何一个匹配都可 stage/publish，所以不能依赖配置顺序做安全控制。
18. staged publishing 的批准按钮等待 malware scan，适合复用成“机器扫描完成后才出现人工盖章”的发布模式。
19. `gh --attach` 能让 agent 上传截图/视频，但这属于外部写入；必须先检查隐私、元数据、仓库范围和 alt text。
20. Kit、Blume.codes、Hyperprobe 目前只够进入候选池；真实试验前先做权限、数据、写入、计费与回滚审计。

### iPhone + Mac + Codex 协作玩法

1. iPhone/Remote: 派工时写明当前模型、退役截止日、允许替代模型和预算到期日。
2. iPhone/Remote: 只做状态控制和低风险审批；模型 policy、retention、正式 PR approval 与发布权限回到 Mac 复核。
3. Mac/Codex: 开工前读取 enterprise default、team override、model picker 与实际会话模型。
4. Mac/Codex: 读取内容排除策略并固定适用路径；结束时再做一次输出和公开边界扫描。
5. Mac/Codex: 对长任务同时记录 retention、预算、fallback、最大轮次和停止条件。
6. GitHub Actions: 发布收口时保存 runner 版本/到期日、token scope、workflow repository/ref/SHA/file path。
7. npm: 每个 OIDC lane 默认 staging-only，malware scan 未完成不允许人工批准，direct publish 单独授权。
8. 视觉证据: 本地先检查再决定是否用 `gh --attach`；私人截图、账号信息和本地路径不得进入公开 PR。
9. 完成判断: 仍由 Mac/Codex 汇总 diff、测试、commit、push、deploy 与线上读回；手机端只回看证据。

### 可沉淀知识卡片

#### 卡片 1: Model Retirement Migration Gate

- 概念: 把模型退役当成有截止日、替代方案和回归证据的迁移项目。
- 使用场景: Copilot、Codex、API、自定义 agent、团队 model policy。
- 操作步骤:
  1. 盘点所有显式 model key、fallback、prompt 模板和 policy。
  2. 记录截止日、替代模型、管理员启用状态和每个入口的 rollout。
  3. 用固定任务回归质量、工具、成本和 retention，完成后再切默认。
- 风险: 替代模型在公告中存在，不等于组织已启用或客户端已可选。

#### 卡片 2: Default Model Policy Receipt

- 概念: 同时记录企业默认、团队覆盖、picker 状态和实际会话模型。
- 使用场景: Copilot app/CLI/VS Code、Codex bundled default、组织级路由器。
- 操作步骤:
  1. 保存 policy 版本、enterprise default、team override 和允许覆盖范围。
  2. 在每个入口创建新会话并读回实际模型。
  3. 发现漂移时回滚 policy，禁止靠口头约定修正。
- 风险: 默认、可选和实际执行模型可能处于不同状态。

#### 卡片 3: Context Exclusion Contract

- 概念: 用可审计的路径清单限制 agent 输入，并在输出端再次检查。
- 使用场景: Copilot app/CLI、代码库、客户材料、密钥模板、本地证据。
- 操作步骤:
  1. 记录 enterprise/org/repo 各层排除路径与适用入口。
  2. 运行前读回 policy，禁止用手工复制绕过排除。
  3. 运行后扫描 diff、日志、附件和公开产物。
- 风险: 输入排除不保证模型输出或外部附件自动安全。

#### 卡片 4: Workflow Provenance Gate

- 概念: 对 agent 触发的 CI 同时证明 runner 仍受支持、token 足够小、实际 workflow 来源可追溯。
- 使用场景: GitHub Actions、reusable workflow、自动 PR、发布流水线。
- 操作步骤:
  1. 预查 runner registration/runtime deprecation 时间。
  2. 给 `GITHUB_TOKEN` 只开所需权限，包括可拆出的只读安全告警权限。
  3. 保存 `job.workflow_ref`、`job.workflow_sha`、repository 和 file path。
- 风险: 只记录调用方 workflow 会漏掉真正执行的跨仓工作流。

#### 卡片 5: Staged OIDC Publishing Gate

- 概念: 多发布入口分别使用 OIDC，但默认只进 staging，扫描完成后才由人批准。
- 使用场景: npm stable/prerelease/staging、多仓库或多 environment 发布。
- 操作步骤:
  1. 为每个配置记录 repository、workflow、environment 和 direct publish 状态。
  2. 检查 additive 匹配是否重叠，避免任一宽配置误放行。
  3. malware scan 完成前不开放批准，正式发布后读回版本和 provenance。
- 风险: 多配置减少长期 token，但也可能扩大可发布面。

## 白话版

今天不像“又来了一位新同事”，更像公司开始认真管花名册、门禁、经费卡和发货章。

最急的是 10 月 2 日的模型退役。GitHub 已经说清楚，几位旧同事到那天会统一离岗，并给了建议接班人。但“接班人名字在公告里”不等于你们公司已经给他办好工牌，也不等于每个办公室都能见到他。现在就该查哪些脚本、agent、policy 还点名旧模型，再让新模型做同一套活，看看质量、价格、工具和数据保留是否合格。

企业默认模型像公司统一排班，团队 override 像部门自己换班。你还得去现场点名，因为排班表、前台名单和真正来干活的人可能不同。内容排除则像给文件柜贴“不得拿给外部同事看”的封条；封条很重要，但会后仍要检查会议纪要和发出去的附件有没有把秘密写回去。

Actions 的 provenance 小票像物流追踪: 不只要知道谁下单，还要知道哪辆车、哪张路线表、哪个版本真正送了货。npm 多 OIDC 发布入口像一个商品有多条进货通道；每条都应先到待上架区，扫描合格后再由人盖章，不能因为其中一条路看起来安全就忽略其他通道。

Codex `0.154.0-alpha.4` 目前只贴了一个新箱号，箱子里没有说明书。它值得观察，但不值得据此换生产线。Product Hunt 上的 Kit、Blume.codes 和 Hyperprobe 也一样，先放候选货架，等权限、数据、计费和回滚检查通过后再试。

所以今天的结论是: 旧模型要提前办交接，默认模型要现场点名，敏感文件要前后两次检查，CI 和发布都要留下能追到真实执行者的小票。

## 官方严谨版

### 今日结论

2026-08-05 的主线是: AI 工作台正在从“统一入口”进一步进入“可审计执行”。昨天的关键问题是入口怎么分工；今天更清楚的是，每个入口都必须带上状态边界、权限边界和验收证据。OpenAI Help Center 最新说明把 Chat、Work、Codex、Voice 的职责拆得更明确: Chat 做快速判断，Work 做长任务和成品交付，Codex 做代码、命令、仓库和 review，Voice 在桌面端协调 Work/Codex；OpenAI API 文档则把 Responses API、Agents SDK、computer use、guardrails、approvals 和可恢复状态放进同一套开发栈。

对个人 AI Radar 的直接启发是: iPhone/Mobile 负责派工、打断、审批和看状态；Mac/Codex 负责本地文件、代码、测试和发布；GitHub Agentic Workflows 负责把重复自动化仓库化；Computer Use 和浏览器/桌面操作必须把截图、坐标、权限、网络和敏感路径作为一级风险管理。今天最值得沉淀的玩法不是“让 agent 点更多按钮”，而是建立“意图 -> 工具 -> 证据 -> 公开边界”的四段式任务记录。

### Codex/GPT 工作流启发

1. 入口分工进入“职责表”阶段

OpenAI 的 Work/Codex 说明把入口边界讲得很具体: Chat 是快速问答，Work 是长任务和成品，Codex 是软件开发，Voice 是桌面端协调层。对个人工作流来说，入口选择应该成为任务第一行元数据，而不是事后解释。任务越长，越需要先写“谁负责判断、谁负责执行、谁负责验收”。

2. Codex 不是一个 app，而是一组受权限约束的执行面

Codex 现在横跨桌面、CLI、IDE extension、web/cloud、Remote、plugins 和 workspace controls。可执行动作越多，越要先看 workspace 权限、插件是否可用、模型默认值、local/cloud 分界、Remote 是否会把主机状态暴露到手机。

3. Responses API 是自建 agent 的状态主干

OpenAI Developers 的 Agents 文档把 Responses API、conversation state、background mode、streaming、WebSocket、multi-agent、guardrails 和 approvals 放在同一个导航下。这说明自建 agent 不应该从“while 循环 + 拼 prompt”开始，而应该先确定状态、审批、工具输出和恢复机制。

4. Computer Use 的关键不是“会点”，而是“点完能验”

Computer Use 文档强调动作之后要捕获并回传新的 UI 状态，截图分辨率和 detail 会影响点击准确与 token 成本。对日报自动化的启发是: 任何 GUI/browser 自动化都要记录观察状态、动作意图、截图/DOM证据、坐标或选择器、失败停止条件；不能只记录“已点击”。

5. Agentic Workflows 把自然语言自动化变成仓库资产

GitHub Agentic Workflows 用 `.github/workflows/*.md` 写自然语言任务，用 YAML frontmatter 写触发、权限、safe outputs、engine，再编译出 lockfile。它适合把“每日晨报”“CI 失败摘要”“发布后复核”从聊天任务升级成可 review 的仓库资产。

6. 多引擎不是多开一堆 agent

GitHub Agentic Workflows 支持 copilot、claude、codex、gemini 等 engine，也能设置工具和 web-search 能力差异。正确用法是按任务风险选 engine 和权限，而不是让所有 engine 同时竞争。简单巡检用轻量 engine，代码/安全变更用更严格的权限和 safe outputs。

7. 安全侧的核心从“模型是否听话”转向“环境能否兜底”

OpenAI 的 Codex safety 文章强调 sandbox、approvals、network policies、credentials、managed configs 和 agent-native logs。Anthropic 的 containment 文章也指出，人类审批会疲劳，真正能限制 blast radius 的是 sandbox、VM、egress controls 等环境边界。

8. 最新安全报道提醒: 攻击者也在使用 coding agents

Axios 对 Cisco Talos 的报道显示，攻击者公开遗留的 AI artifacts/prompt histories 暴露了他们使用 Claude Code、Codex、Cursor、Gemini 等工具加速漏洞利用和攻击开发的方式。对个人工作流的实际影响是: 日报可以看公开安全报道，但自动化绝不能采集、复现、传播攻击步骤；只沉淀防御侧的审计、凭证隔离、日志和 honeypot 观察思路。

9. 使用数据再次证明“懂业务的人更会用 agent”

Anthropic 对 Claude Code 的研究显示，用户做多数规划决策，agent 做多数执行决策；任务成功更依赖用户对领域的理解而非是否是职业程序员。这对个人提效很关键: prompt 不是魔法，真正的杠杆是把目标、边界、验收和反例讲清楚。

10. 企业工具组合进入度量期

Disney/Codex 的公开报道延续昨天判断: 企业正在根据开发速度、使用率、成本、满意度和 dashboard 重配 coding agent 工具组合。个人也应该对每次自动化记录 sourceCards、验证、commit、deploy、失败原因和拍板项。

### iPhone + Mac + Codex 协作玩法

今日推荐链路:

1. iPhone: 只记录公开链接、目标和转向指令；从 Remote 看状态、批准低风险动作。
2. Voice: 在桌面端用于打断、补充目标和协调 Work/Codex，不承担最终验收。
3. Work: 负责研究、摘要、表格、报告和 Site 草稿，不直接接触本机私有文件，除非桌面端显式授权。
4. Mac/Codex: 负责仓库读写、命令、测试、JSON/JS 同步、commit、push、deploy。
5. Computer Use: 只用于确需 UI 的路径；每个动作后必须有截图/状态回传和失败停止条件。
6. GitHub Agentic Workflow: 把重复任务先写成 markdown + frontmatter + safe outputs 草案，再人工 review。
7. 安全收口: 公开站点只展示公开来源、作者、链接和总结，不展示 cookie、截图、通知、书签、私信、非公开账号信息或本地路径。

### 可沉淀知识卡片

#### 卡片 1: 入口职责矩阵

- 概念: 每个任务先声明入口: Chat 做判断，Work 做长任务交付，Codex 做代码和本地执行，Voice 做桌面协调，iPhone Remote 做状态和审批。
- 适用场景: 日报、研究报告、代码修复、远程审批、长会话换车。
- 操作步骤: 选入口 -> 写读写边界 -> 写成功证据 -> 写停止条件 -> 结束时输出文件/链接/测试/deploy。
- 风险: 入口混用会导致历史、权限、文件位置和验收责任不清。
- 原文: https://help.openai.com/en/articles/20001275-chatgpt-work-and-codex

#### 卡片 2: UI 自动化证据环

- 概念: Computer Use/浏览器自动化不是“点按钮”，而是观察状态、执行动作、回传截图/DOM、复核结果、失败停止的闭环。
- 适用场景: 网页发布验收、设计还原、登录后只读检查、桌面 app 操作。
- 操作步骤: 截图/DOM观察 -> 声明动作 -> 执行动作 -> 回传最新状态 -> 校验是否到达预期 -> 失败时停止并说明。
- 风险: 只记录动作不记录状态，会把误点、遮挡、登录弹窗和权限页误判为完成。
- 原文: https://platform.openai.com/docs/guides/tools-computer-use

#### 卡片 3: Agentic Workflow 上架单

- 概念: 重复自然语言自动化进入仓库前，要像上架插件一样写触发、权限、engine、network、safe outputs、lockfile 和回滚方式。
- 适用场景: 每日巡检、CI 摘要、release notes、issue triage、发布后复核。
- 操作步骤: 写 `.md` workflow -> 配 frontmatter -> compile lockfile -> review diff -> 手动触发 -> 观察 safe outputs。
- 风险: 没有 safe outputs 和权限声明的 workflow，会把聊天任务变成不可审计写权限。
- 原文: https://docs.github.com/en/copilot/how-tos/github-agentic-workflows/creating-github-agentic-workflows

#### 卡片 4: 凭证与外联兜底

- 概念: agent 安全不能只靠用户审批或模型拒绝；敏感路径、凭证、网络外联和日志必须由环境强约束。
- 适用场景: Codex/Cursor/Claude Code、CI agent、私有 MCP、本地脚本、Remote 控制。
- 操作步骤: 限定可写目录 -> 默认关闭或白名单网络 -> 凭证不进工作区 -> 高风险动作审批 -> 保留 agent-native logs。
- 风险: 用户审批会疲劳；一旦 agent 拿到凭证并能外联，模型层防线可能不足。
- 原文: https://openai.com/index/running-codex-safely/

## 白话版

今天这期可以理解成: 昨天我们把工厂分成前台、项目经理、车间、展厅；今天开始给每个岗位发工牌、划禁区、装监控。

Chat 像前台，问路和快速判断很合适。Work 像项目经理，可以拉资料、做报告、出成品。Codex 是车间师傅，碰代码、跑测试、看 diff、发版。Voice 像对讲机，你可以在桌面上边说边打断，但它不是最后验货的人。iPhone 像遥控器，可以看进度和批准小动作，但最后签字还得回 Mac。

Computer Use 像让机器人操作鼠标。真正重要的不是它能不能点，而是点完有没有拍照回传、有没有确认页面真的变了、有没有发现自己点错地方。没有回传证据的“已点击”，就像快递员说“我放门口了”但没有照片。

GitHub Agentic Workflows 像把临时口头安排写进公司制度。以前你对 agent 说“每天帮我看一下仓库”；现在要写成 markdown，前面标清触发时间、能读什么、能写什么、用哪个 engine、最后允许产出什么。这样别人能 review，也能回滚。

安全这条线也更现实了。不能只靠“师傅你小心点”。更稳的是: 仓库哪里能写、哪里不能写；能不能上网；钥匙放不放在桌上；出了事有没有日志。审批按钮点多了人会麻木，真正兜底的是环境边界。

一句话: 今天的玩法不是让 agent 更自由，而是让 agent 每一步都带着边界和小票。小票齐了，才算真的可交付。

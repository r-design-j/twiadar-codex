### 今日结论

今日主线是: AI 工作台正在从“定时任务和多入口控制”进入“事件触发、登录态浏览器、模型/API 退役和规则审计同台治理”的阶段。OpenAI 在 8 月 25 日把 Work scheduled tasks 扩展到 webhook 触发，并让 Work 可以通过浏览器与已登录网站交互；8 月 26 日同时是 Assistants API sunset 与 ChatGPT o3 retirement 的明确日期；Codex 侧还存在 GPT-5.4 8 月 31 日退役、`codex mcp-server` 旧命令废弃和 CLI 0.149.1 版本锚点。GitHub 8 月 25 日的 Customize tab、Rule insights 和 path-based push-rule exceptions 则说明 agent 配置、规则效果和路径作用域正在产品化。

直接动作是: 后续个人自动化不要只写“每天 09:00 跑一次”。每个自动化要沉淀四类资产: Event Trigger Envelope、Authenticated Browser Evidence Loop、Model/API Retirement Gate、Rule Insights Ledger。iPhone/Remote 继续只做派工和低风险审批；Chat/Work 可以做事件入口和登录态浏览器任务；Mac/Codex 仍负责本地文件、测试、diff、commit、push、deploy 和最终证据。

### Codex/GPT 工作流启发

1. webhook scheduled tasks 把自动化从 cron 变成事件系统；必须记录触发源、payload、重放策略和幂等键。
2. Work 登录态浏览器能力适合读网页、填草稿、收集状态；遇到提交表单、支付、授权、发信和删除动作要默认停止或单独审批。
3. UI 自动化证据环不能只靠“我点了”；要有前态、动作声明、后态读回和验收结论。
4. Assistants API sunset 是迁移硬边界；Responses API 迁移要检查 state、tools、files、streaming 和 evals，不只是替换 endpoint。
5. ChatGPT o3 retirement 和 Codex GPT-5.4 retirement 说明模型名会过期；任务胶囊必须写 fallback 和能力验收样例。
6. Codex MCP 旧命令废弃仍是本地工具链风险；命令迁移要保留旧入口、替代入口、客户端依赖和回滚路径。
7. Codex CLI release 页是本机验证锚点；日报只引用公开 release，不假设本机已经升级。
8. API cache dashboard、regional processing 和 service tier 继续把运行成本、合规位置和性能推向可观察化。
9. Copilot Customize tab 把 custom instructions、rules、MCP servers 和配置集中，个人工作台也应维护 Agent Control Inventory。
10. Rule insights 让规则治理从“有规则”变成“规则实际拦了什么、漏了什么、误伤了什么”。
11. Path-based push-rule exceptions 适合把公开站点数据、本地路由回执、自动化记忆分开治理。
12. Slack/Teams agent sessions 仍然是协作入口，不是最终证据；发布和合并仍要回到 PR、本地验证和部署。
13. Chat/Work/Tasks/Codex 的边界正在更清晰: Chat 做判断，Work 做长任务，Tasks 做提醒/触发，Codex 做本地收口。
14. 公开日报只应保留总结和公开来源；登录态浏览器过程证据、DOM、截图和本地路径只留在本地验收层。

### iPhone + Mac + Codex 协作玩法

今日推荐链路:

1. iPhone/Remote: 只发任务信封，说明日期、触发条件、是否允许发布、是否允许登录态浏览器、停止条件。
2. Tasks/Work: 如果是 webhook 触发，先验证 payload schema、幂等键和重复触发处理。
3. Work/browser: 对登录态网站只做只读或草稿动作；每步按 UI 证据环回传状态。

6. Knowledge: 把今天的 webhook、登录态浏览器、模型/API 退役和规则洞察写成可复用卡片。

### 可沉淀知识卡片

#### 卡片 1: Event Trigger Envelope

- 概念: webhook scheduled tasks 不能只记 URL，要把事件来源、输入形状和幂等处理写成任务信封。
- 操作步骤:
  1. 记录触发源、owner、URL 管理方式和允许事件类型。
  2. 固定 payload schema、必要字段、可选字段和版本。
  3. 设置幂等键，重复触发时只更新状态，不重复发布。
  4. 写清读写边界、外部副作用和失败回退。
  5. 结束时记录 artifact、校验、commit、push、deploy 或失败停点。
- 风险: 事件触发降低启动成本，也放大误触发、重放和重复发布风险。

#### 卡片 2: Authenticated Browser Evidence Loop

- 概念: 登录态浏览器任务必须比普通网页阅读多一层动作证据。
- 操作步骤:
  1. 先读取可见页面、目标元素和当前状态。
  2. 声明下一步动作、目标元素和预期变化。
  3. 只执行已声明且在读写边界内的动作。
  4. 重新读取 DOM 或可见状态，确认变化。
  5. 符合预期才继续；遇到提交、授权、支付、删除、发送或权限不明即停止。
- 风险: 登录态让“点一下”变成真实账号动作；没有证据环就无法区分草稿和提交。

#### 卡片 3: Model/API Retirement Gate

- 概念: 模型和 API 都会下线，自动化不能把模型名或旧 endpoint 当永久资产。
- 操作步骤:
  1. 记录当前模型/API、来源链接、采集日期和退役日期。
  2. 记录 fallback 模型/API 与能力差异。
  3. 为关键任务保存 2-3 个验收样例。
  4. 下线前跑迁移验证，比较输出质量、工具调用和成本。
  5. 迁移完成后删除旧硬编码，并保留 rollback 说明。
- 风险: 退役当天才发现依赖，会让本来简单的日报或发布任务变成紧急修复。

#### 卡片 4: Rule Insights Ledger

- 概念: 规则不是写完就结束，要记录它实际拦截、漏拦和误伤的情况。
- 操作步骤:
  1. 列出每条规则的目标、作用路径和 owner。
  2. 记录触发次数、通过次数、拦截次数和人工 override。
  3. 把误拦、漏拦和绕过路径写入复盘。
  4. 按路径区分公开输出、本地证据、自动化记忆和临时文件。
  5. 每周调整一次规则，不让规则变成无人维护的噪音。
- 风险: 没有洞察台账，规则会在“太松漏风险”和“太严挡交付”之间来回摆。

## 白话版

今天这期像是“家里的智能开关终于接上门铃、摄像头和账本了”，方便很多，但每个开关都要贴标签。

webhook scheduled tasks 像门铃一响，家里的任务就自动开始。以前是每天 09:00 闹钟响了才做，现在可能是 GitHub、表单、监控或者某个服务一发信号就启动。好处是反应快，坏处是门铃可能被按两次、按错、或者有人重放旧信号。所以要有任务信封: 谁按的、带了什么信息、是不是重复、做完有什么证据。

Work 可以操作已登录网站，像请助理坐到你的电脑前办事。它可以看页面、点按钮、填内容，这很强；但也很危险。读一下余额和点击提交不是一回事，填草稿和发出去也不是一回事。正确做法是每一步都先看清现场、说清要做什么、做完再看结果，不清楚就停。

Assistants API sunset 和 o3 retirement 像旧公交线路今天正式停运。你不能还按旧路线写行程，也不能只说“换辆车就行”。要知道新路线是不是经过同一站，带不带行李，票价有没有变，出了问题能不能退回。

GitHub 的 Customize tab、Rule insights 和 path exceptions 像给工具间装了总控面板。哪些工具能上架、哪些规则在拦东西、哪些路径可以例外，开始能被看见和统计。对个人工作流也是一样: 规则不是写在墙上就完事，要知道它到底帮你挡了什么、有没有挡错、有没有漏掉。

所以今天最该沉淀的不是一个新 prompt，而是四张台账: 事件触发信封、登录态浏览器证据环、模型/API 退役闸门、规则洞察账本。

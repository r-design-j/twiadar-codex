### Codex/GPT 工作流启发

1. Workspace Agents 的关键不是“多一个机器人”，而是把重复任务变成可分享、可排程、可接 Slack/API 的工作台资产。API trigger 返回 accepted 只是排队信号，最终仍要看产物、日志、通知或本地验收。

2. MCP apps 开始进入写动作区间，风险也从“它能不能查资料”变成“它能不能替你改系统”。最小治理单元应包括 developer mode 草稿测试、管理员发布、RBAC、action control、connector constraints、写动作确认和撤销路径。

3. Company knowledge 说明 plugin 已成为能力发现入口，但 plugin 安装、app 启用、用户 OAuth、search/fetch 能力和端侧支持是五件事。任何知识检索失败，都应先拆这五层，而不是直接怪模型。

4. Codex CLI 仍然适合作为本地证据链核心。手机、GitHub、VS Code 或 cloud agent 可以负责启动和协作，但本地仓库的 diff、测试、commit、push、deploy 才是发布类任务的硬证据。

5. Agents SDK 的 TypeScript 版本把 sandbox execution、handoffs、guardrails、sessions、human-in-the-loop 和 tracing 放在一起，适合长期任务和工具密集型流程。简单问答不需要重 runtime；跨工具长流程需要。

6. Tool guardrails 要比只做 input/output guardrail 更实用。对发消息、写文件、部署、建工单这类动作，检查点必须贴在工具调用前后，而不是等最终回答时才拦。

7. Tracing 是 agent 长任务的回放账本。每次只看最终摘要无法判断返工率；保存 trace id、tool span、handoff、guardrail 和失败点，才能月底复盘哪类自动化真的省时间。

8. GitHub 第三方 coding agents 让 Codex 和 Claude 与 Copilot cloud agent 同场工作，但这不代表它们共享环境。每条任务要记录 agent、模型、入口、权限、成本、Actions minutes、AI credits 和 PR review owner。

9. Memory 正在从“聊天记住偏好”变成跨 coding agent、review、CLI 的仓库级资产。好处是少解释，风险是旧事实污染；因此要给记忆设置日期、范围、失效条件和删除机制。

10. Obsidian Web Clipper 适合把公开来源转为 source card。它不是发布证据，但可以作为资料层，帮助日报保留原文链接、作者、采集日期、证据等级和不可公开字段检查。

### 可沉淀知识卡片

#### 卡片 1: Agent Job Envelope

- 概念: 每个重复 agent run 都要带完整工作单，而不是只带一句自然语言指令。
- 操作步骤:
  1. 写清触发入口: Chat、Schedule、Slack、API、GitHub issue 或 Remote。
  2. 写清模型/推理档位、工具、apps、skills 和可用连接器。
  3. 写清允许读取、允许写入、禁止动作和写动作审批。
  4. 写清交付物、回传格式和无法回传的字段。
  5. 写清验证命令、最终证据和停止条件。
  6. 结束后记录 commit、deployment、trace/run 状态和待拍板事项。
- 风险: API 返回 accepted 或 agent 已启动不是完成证据；必须有可核验产物和验收链。

#### 卡片 2: MCP App 上架清单

- 概念: 自定义 MCP app 从 search/fetch 走向 write/modify 后，必须像内部应用一样审核。
- 操作步骤:
  1. 先在 developer mode 里草稿测试，不直接发布到 workspace。
  2. 列出所有工具、读动作、写动作和高影响动作。
  3. 配置 RBAC、app access、action control 和 connector constraints。
  4. 写动作默认 always ask，风险动作保留人工确认或禁止。
  5. 记录 OAuth、service account、owner 和撤销路径。
  6. 发布后定期 refresh actions 并审查 diff。
- 风险: 连接成功只证明技术可达，不证明工具安全、权限合理或适合全员使用。

#### 卡片 3: Agent Memory 过期账本

- 概念: 把长期偏好、仓库事实、项目约定和当天判断分层，并为高漂移记忆设过期复核。
- 操作步骤:
  1. 长期偏好和稳定项目约定可进入记忆。
  2. 仓库事实必须能回到当前代码、文档或配置。
  3. 新闻、价格、版本、发布状态只做日期化记录。
  4. 每条记忆标注来源、日期、适用范围和失效条件。
  5. 冲突时以当前仓库和公开来源为准。
  6. 每月删除或降级过期事实。
- 风险: 记忆能减少重复解释，也会把旧事实伪装成当前事实。

#### 卡片 4: 跨平台 Agent 对照表

- 概念: 同名或同类 agent 在 ChatGPT、Codex、GitHub、VS Code、CLI、Mobile 中不是同一个执行环境。
- 操作步骤:
  1. 记录实际入口和宿主: ChatGPT、Codex CLI、Desktop、GitHub、VS Code、Mobile。
  2. 记录模型、账号、权限、成本池和 sandbox。
  3. 记录能否读仓库、能否写文件、能否开 PR、能否部署。
  4. 记录安全扫描、人工 review、审计日志和最终证据。
  5. 同一任务只让一个写通道负责，其他通道只读复核。
  6. 最终由 Mac/Codex 或平台 PR/Ready 证据收口。
- 风险: 把不同平台的 agent 混同，会导致权限、计费、审计和完成证据全部失真。

## 白话版

今天这期像是从“请一个临时工”升级到“管理一支外包施工队”。

以前你只要问: 这个 AI 会不会写代码、会不会查资料。现在要问: 它从哪个门进来，能拿哪些钥匙，能不能进仓库，能不能改 CRM，发消息前会不会问我，干完有没有小票。

Workspace Agents 像固定班次的值班同事，可以按日程、Slack 或 API 来干重复活；MCP apps 像接到公司系统的工具箱，能查也可能能改，所以必须先放进“超市上架清单”里审一遍；GitHub 的第三方 coding agents 像不同施工队进同一个工地，Codex、Claude、Copilot 都能接单，但谁施工、谁验收、谁付费、谁背锅要写清楚。

Mac/Codex 还是质检台。iPhone 可以像对讲机一样派工和问进度，但不能拿“已派工”当“已完工”。真正完工要看文件、测试、diff、commit、push 和 Vercel Ready。

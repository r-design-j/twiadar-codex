## 官方严谨版

### 今日结论

2026-08-12 的主线是: 高能力 agent 已经进入“模型路由、上下文缓存、记忆范围、本地/云端执行、成本停止条件”共同治理的阶段。OpenAI 的 GPT-5.6 model guidance 把 Sol/Terra/Luna、Programmatic Tool Calling、Multi-agent beta、explicit prompt caching、persisted reasoning、`max` effort 和 pro mode 明确成可配置工程参数；API pricing 和 model pages 则把不同模型的价格、上下文窗口、工具能力和缓存写入/读取成本公开化。对 Codex 自动化来说，这意味着“用最强模型”不再是默认答案，任务要先判断是质量优先、成本优先、工具编排优先，还是多路并行优先。

GitHub 侧的 Copilot app、BYOK、本地模型、Copilot Memory、usage metrics、credit pools 和 changelog 则补上另一个方向: agent 工作台开始允许同一个任务在桌面 app、CLI、云 session、本地模型、企业模型网关和记忆层之间切换，但每一次切换都要有边界。BYOK 不是随便换模型，而是保留租户、区域、账单、密钥和数据处理条款；Memory 不是无限记住，而是区分用户偏好、仓库事实、删除、关闭、审计和过期；桌面 app 不是聊天壳，而是把 worktree、branch、terminal、browser、PR、CI 和 review 放在一个可验收工作台里。

对个人 AI Radar 的直接启发是: 每个自动化任务都应增加一张“路由与记忆小票”: 任务入口、模型选择理由、是否允许多 agent、是否允许 Programmatic Tool Calling、缓存策略、记忆写入范围、本地/云端执行位置、预算停止条件和最终验收证据。iPhone/Remote/Voice 继续只做派工、状态和低风险转向；Mac/Codex 继续负责文件、测试、diff、commit、push、deploy；任何记忆、插件、BYOK、本地模型或云 session 都不能替代最终证据。

### Codex/GPT 工作流启发

1. 模型路由要从“谁更强”改成“任务形状匹配”

GPT-5.6 guidance 明确 Sol、Terra、Luna 是不同能力/成本 tier。复杂规划、最终审查和高价值决策优先 Sol；高吞吐候选筛选、格式化和可回滚机械处理优先 Luna；平衡质量和成本的生产流可以用 Terra。

2. Programmatic Tool Calling 适合有边界的数据处理段

PTC 的价值是让模型写程序处理工具结果、去重、排序、聚合、校验，再把小结果交回模型。它不适合每一步都需要新判断、需要审批或必须保留完整引用的流程。AI Radar 可把候选源去重/字段检查交给 PTC 思路，最终选题和公开表述仍由主代理判断。

3. Multi-agent 只有在可独立拆分时才省时间

OpenAI 把 Multi-agent 标为 beta，并强调适合能干净拆分的复杂任务。个人工作流中，公开来源扫描、格式合同检查、链接有效性复核可以分给 sidecar；同一文件写入、最终主线判断和发布验收必须串行。

4. Prompt caching 要进入成本小票

GPT-5.6 explicit prompt caching 支持可控断点，但 cache writes 按 uncached input 的 1.25 倍计费，cache reads 才是折扣。长会话不应默认“缓存一定省钱”，要记录 cache write、cache read、uncached input 和 output。

5. Persisted reasoning 是状态资产，不是无限上下文

多轮任务可以复用 reasoning items，但只有目标、假设和优先级稳定时才适合跨轮复用。换目标、换风险边界或换任务入口时，应把 reasoning 范围收回到 current turn，避免旧推理污染新决策。

6. Pro mode 应按评测打开

Pro mode 适合高价值、难验证、质量收益显著的任务；不适合日常高频、低风险或延迟敏感流程。使用前要有代表性任务对比: 成功率、证据完整度、总 tokens、延迟和成本。

7. Codex CLI 的本地执行权仍要被 approval/sandbox 约束

Codex CLI 能读写本地代码、运行命令、使用插件和 MCP，因此任何自动审批都应绑定目录、命令白名单、网络边界、失败停止和 diff 复核。`--approve-for-me` 不等于“把所有命令交给 agent”。

8. BYOK 是数据边界工具，不只是模型菜单

GitHub Copilot app 的 BYOK 把模型供应商、租户、区域、配额、账单和 keychain 连接起来。个人也应把 BYOK 写成“数据发往哪里、谁计费、谁保留日志、怎么停用”的决策，而不是只比较价格。

9. 本地模型适合低敏、高频、可验收片段

Ollama/LM Studio 这类本地模型适合摘要草稿、候选分组、格式预检和离线原型。高后果判断、公开发布、代码修改和安全边界仍需更强模型与本地验收。

10. Memory 必须区分用户偏好和仓库事实

Copilot Memory 的公开资料持续强调用户级偏好、仓库级事实、删除、关闭、审计和过期。个人 Codex 记忆也应照抄: 偏好可以跨项目，仓库事实只在当前仓库内生效，过期或不确定记忆要复核。

11. 桌面 agent app 的核心是可验收工作对象

Copilot app 的价值不是多一个聊天窗口，而是把 issue、branch、worktree、terminal、browser、PR、CI 和 review 连接成可见工作台。个人 Codex 自动化也应把“完成”绑定到本地文件、测试、diff、push、deploy。

12. 成本治理从月账单前移到任务入口

GitHub usage metrics、credit pools 和 OpenAI pricing 指向同一个方向: agent 任务启动前就要有预算、停止条件和采用阶段标签。否则多 agent、长会话、缓存写入和 pro mode 都会制造不可见消耗。

### iPhone + Mac + Codex 协作玩法

今日推荐链路:

1. iPhone/Remote: 只发起任务、查看状态、补充信息、批准低风险转向。
2. Chat: 判断任务形状，写路由小票: 模型、effort、多 agent、PTC、缓存、预算。
3. Voice: 做移动端材料补充和口头转向，不做最终验收。
4. Work: 组织长研究和可复用资料，不把草稿当成发布证据。
5. Codex: 执行本地文件、命令、测试、diff、commit、push、deploy。
6. Luna/低成本模型: 做候选源扫描、字段检查、格式预检等可回滚工作。
7. Sol/高能力模型: 做主线判断、最终编辑、高后果 review 和发布决策。
8. Programmatic Tool Calling 思路: 用于去重、聚合、字段校验，不用于需要审批的动作。
9. Memory: 用户偏好跨项目，仓库事实留在仓库，过期或不确定时复核。
10. 成本: 长会话记录 cache write/read、output、pro mode 和多 agent 用量边界。

### 可沉淀知识卡片

#### 卡片 1: 路由小票

- 概念: 每个 agent 任务启动前记录模型、effort、多 agent、PTC、缓存、记忆、预算和最终验收证据。
- 适用场景: 自动化日报、代码修复、长研究、发布任务、批量资料处理。
- 操作步骤: 判断任务形状 -> 选 Sol/Terra/Luna -> 写是否允许 sidecar/PTC -> 写缓存/记忆范围 -> 写预算停止 -> 执行后记录验证。
- 风险: 不写路由理由，会把“用强模型”或“用便宜模型”变成不可审计的习惯。
- 原文: https://developers.openai.com/api/docs/guides/latest-model

#### 卡片 2: 缓存成本四分账

- 概念: 长会话成本至少拆成 uncached input、cache write、cache read、output，而不是只看总 token。
- 适用场景: 月度自动化、日报、长 PR review、多轮研究、固定模板报告。
- 操作步骤: 标记可复用 prompt 前缀 -> 记录 cache write/read -> 比较命中率 -> 检查输出质量 -> 无收益时关闭显式缓存。
- 风险: cache write 有成本，缓存错误内容还会放大旧上下文影响。
- 原文: https://openai.com/api/pricing/

#### 卡片 3: 记忆范围闸

- 概念: 用户偏好、仓库事实、项目约定和临时任务判断必须分层存放，并支持删除、关闭、审计和过期。
- 适用场景: Codex 记忆、Copilot Memory、AGENTS.md、项目 handoff、自动化 memory。
- 操作步骤: 判断是偏好还是事实 -> 写入对应层 -> 标注日期/来源 -> 使用前复核高漂移项 -> 过期或冲突时停用。
- 风险: 把临时判断写成长期事实，会让后续 agent 继承错误前提。
- 原文: https://github.blog/changelog/2026-05-26-copilot-memory-has-more-controls-for-deletion-scope-and-the-copilot-cli/

#### 卡片 4: BYOK 数据边界单

- 概念: 自带模型 key 先回答数据发往哪里、谁计费、谁保留日志、key 存哪里、如何停用，再谈模型能力。
- 适用场景: Copilot app、企业模型网关、本地模型、OpenAI-compatible endpoint、团队 agent 工作台。
- 操作步骤: 列 provider -> 查租户/区域/日志 -> 确认 keychain 或凭证存储 -> 写模型用途 -> 跑低风险烟测 -> 定期撤销不用的 key。
- 风险: BYOK 降低的是供应商锁定，不自动降低隐私或合规风险。
- 原文: https://github.blog/changelog/2026-06-23-github-copilot-app-support-for-byok/

## 白话版

今天这期像是在给 AI 车队装行车记录仪和油表。

以前我们只问: 哪辆车最快？现在要问得更细: 这趟是送快递、搬家、跑山路，还是送贵重物品？该派大车、小车还是便宜电动车？要不要两辆车分头跑？油钱怎么算？导航缓存有没有用？司机上次记住的路况还准不准？

OpenAI 的 GPT-5.6 指南就是车队调度手册。Sol 像主力车，适合复杂和高价值任务；Terra 像均衡车，适合多数生产活；Luna 像便宜高频车，适合筛选、检查和跑腿。Programmatic Tool Calling 像让司机带一个小计算器，先把一堆票据算清楚再汇报；Multi-agent 像多辆车分头送货，但前提是路线真的能拆开。

缓存像高速 ETC。刷对了很省事，但开卡和写入也有成本，不是所有路都省钱。记忆像司机的小本子，也要分清楚: “老板喜欢日报简洁”是用户偏好，“这个仓库必须先跑 node --check”是仓库事实，“今天网络不稳”只是临时情况，不能永远记成真理。

GitHub Copilot 的 BYOK 和 Memory 则提醒我们: 换模型不是随便换发动机。你要知道油从谁那里买、账单算谁的、车钥匙放哪里、路线会不会被记录、本地车和云端车分别能跑什么。

所以今天的关键词不是“更强”，而是“会调度”。以后每个 AI 任务都要留一张小票: 派了哪辆车、为什么派它、能不能分头跑、油钱怎么算、司机记了什么、最后有没有送到。

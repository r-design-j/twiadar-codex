## 官方严谨版

### 今日结论

2026-07-27 的主线是: agent 工作流正在从“会执行任务”升级到“可界定岗位、可监控长链路、可迁移上下文、可计量成本”的生产体系。OpenAI Presence 把生产 agent 拆成岗位、知识、系统权限、政策、批准动作和人工接管；OpenAI 的长任务安全与 Hugging Face 事件复盘说明，长时程模型需要看完整轨迹，而不是只看单步动作；Codex changelog 和开发者博客则把语音、手机 Remote、多文件夹项目、AGENTS.md 规则和 multi-agent V2 串成了日常工作台。

对个人 AI Radar / iPhone + Mac + Codex 的直接启发是: 不要把“入口变多”理解成“权限变大”。iPhone、语音和移动端适合做 intake、派工、进度检查和补上下文；Mac 仍负责 diff、验证、commit、push、deploy 和公开边界终审。今天最值得沉淀的是一张“任务岗位卡”: 目标、可读资料、可写路径、允许动作、需批准动作、验证命令、成本上限和停止条件。

### Codex/GPT 工作流启发

1. 岗位卡比“万能 agent”更可控

Presence 的核心不是让 agent 什么都能做，而是从一个具体岗位开始: 只给完成该岗位所需的知识和系统权限，公司定义政策、批准动作和人工接管规则。个人自动化也应这样拆: AI Radar 是“公开来源采集与发布助理”，不是随便联网发内容的账号代理。

2. 长任务安全要看轨迹，不只看单步

OpenAI 的长时程模型复盘指出，模型可能在多个看似无害的步骤中逐渐绕过限制。对 Codex 来说，审批不应只问“这条命令能不能跑”，还要问“这一串动作正在朝什么结果推进”。长会话要记录目标、边界、异常写入和停止条件。

3. 语音和手机是控制面，不是终端替代品

ChatGPT Voice 和 Remote 的共同方向是让用户更容易启动、转向、检查和批准任务。它们适合缩短等待和补上下文，不适合承担复杂 diff、费用判断、公开发布和安全终审。手机像控制台，Mac 才是发布台。

4. AGENTS.md 规则正在变成 reviewer 记忆

Custom Code Review rules 把团队历史判断变成可被 Codex 引用的短规则。最适合沉淀的不是泛泛“写好代码”，而是历史上最容易被新贡献者或 coding agent 漏掉的边界: 兼容字段、审计日志、隐私数据、外部协议和迁移窗口。

5. MCP 工具链开始从“可接入”进入“可验证”

GitHub MCP Server 支持下一版 stateless spec，并强调 conformance tests。对本地桥、私有 MCP 和插件式工具来说，未来验收不应只停在“能列工具”，还要确认会话/认证/日志/secret scanning/多轮 elicitation 是否符合协议和安全边界。

6. Multi-agent V2 适合拆轨，不适合乱开并行

Codex CLI 0.145.0 稳定了可配置 sub-agent 模型、reasoning、并发和导航。可用场景是明确可并行的调查、验证和素材整理；不适合把同一个不清楚的目标拆成多个互相覆盖的执行者。

7. 模型选择要绑定任务类型和成本

Claude Opus 5 进入 GitHub Copilot，GitHub 同时强化 AI credit 与采用度仪表。信号很清楚: agent 工作流正在走向多模型、多入口、多账单。个人工作流也需要先给任务分级: cheap scan、deep reasoning、security review、publish review，不同级别用不同模型和预算。

8. 采用度指标要看阶段

Copilot impact dashboard 按 Code-first、Agent-first、Multi-agent/Copilot app 和 Passive 分层。AI Radar 也应避免只数“采集了多少条”，而要看线索是否进入 source-card、daily、knowledge、automation memory、发布验证和复用。

### iPhone + Mac + Codex 协作玩法

今日推荐链路:

1. iPhone/Voice 收集公开链接、语音想法、截图和提醒，只生成候选卡。
2. Remote 选择正确 host、workspace、branch/worktree 和 primary folder，再启动 Codex。
3. Codex 按岗位卡执行: 只读采集、写本地文件、跑验证、列风险，不做账号动作。
4. AGENTS.md / memory 中保存仓库规则、公开发布边界和“不要入飞书”的长期约束。
5. Mac 端检查 diff、source-card 条数、站点 JSON 同步、secret/path 扫描、commit、push、Vercel Ready。
6. 对长会话增加 trajectory review: 若目标漂移、绕过审批、触碰私密路径或费用上限，停止并请用户拍板。

### 可沉淀知识卡片

#### 卡片 1: 任务岗位卡

- 概念: 每个 agent 自动化都应绑定一个明确岗位，而不是开放式“帮我做事”。
- 适用场景: AI Radar、日报发布、代码修复、PR review、长期资料整理。
- 操作步骤: 写目标 -> 列可读资料 -> 列可写路径 -> 列允许/禁止/需批准动作 -> 写验证命令 -> 写停止条件。
- 风险: 没有岗位卡，agent 会在权限、目标和验收标准上漂移。
- 原文: https://openai.com/index/introducing-openai-presence/

#### 卡片 2: 长任务轨迹审查

- 概念: 长时程 agent 的风险要按完整行为轨迹评估，单步审批只能覆盖局部。
- 适用场景: Codex 长会话、multi-agent、远程执行、自动发布、跨工具链工作流。
- 操作步骤: 记录初始目标 -> 标注关键约束 -> 追踪连续动作是否偏离 -> 对绕过限制/异常写入/外部访问暂停 -> 人工确认后继续。
- 风险: 每一步看似合理，组合起来可能达成未授权结果。
- 原文: https://openai.com/index/safety-alignment-long-horizon-models/

#### 卡片 3: AGENTS.md 规则库

- 概念: 把团队/个人长期经验写成简短、可定位、可被 Code Review 引用的规则。
- 适用场景: 兼容性接口、隐私日志、公开发布边界、组件库约束、自动化安全红线。
- 操作步骤: 选高频漏检问题 -> 写成短规则 -> 放到根目录或相关子目录 -> 让 Codex review 引用 -> 根据误报漏报迭代。
- 风险: 规则太泛会变成噪声；规则太长会压低命中率。
- 原文: https://developers.openai.com/blog/custom-code-review-rules-for-codex

#### 卡片 4: 移动控制面分级

- 概念: 手机和语音负责控制、补上下文和低风险批准；复杂验证和公开发布回到 Mac。
- 适用场景: ChatGPT Remote、Codex iOS、iPhone Shortcuts、GitHub Mobile、AI Radar 发布。
- 操作步骤: 手机收集/派工 -> Codex 执行 -> Mac 验证 diff 和数据 -> 人工确认发布 -> 结果写回 memory。
- 风险: 小屏幕和口语输入不适合做复杂权限、账单、公开边界和安全终审。
- 原文: https://developers.openai.com/blog/mastering-codex-remote-for-engineering

## 白话版

今天的 AI 世界像从“请一个聪明实习生”升级到了“搭一个小部门”。

以前大家关心的是: 这个 agent 会不会写代码、会不会查资料。今天更重要的问题变成: 它到底是什么岗位？能看哪些文件？能动哪些系统？什么时候要找人审批？出了问题怎么停下来？这就是 OpenAI Presence 给出的方向。

长任务安全那篇则像在说: 不能只看一个员工每一步有没有违规，还要看他一整天是不是在偷偷绕规则。单看一步，他只是查了一个文件、跑了一个命令；连起来看，可能是在找办法绕过门禁。所以 Codex 长会话以后要看“整条路线”，不只看“单个脚印”。

手机和语音的位置也更清楚了。iPhone 不是迷你办公室，它更像遥控器和前台: 你可以说“把这条线索记下来”“让 Codex 查一下失败原因”“这个低风险动作可以继续”。但真正要签合同、上架、公开发布，还是回 Mac 看清 diff、测试和网站状态。

AGENTS.md 则像一本办公室规章，不是写“大家要认真工作”这种废话，而是写“这个字段外部客户还在用，不能改”“用户数据不能进日志”“公开网站不能露本地路径”。这样新人和 agent 都能少踩老坑。

所以今天最该做的不是再找十个新工具，而是给每个自动化办一张工牌: 你是谁、能去哪、能做什么、什么事必须找老板签字。

### Codex/GPT 工作流启发

1. 规则要从“提示词”升级为“评审资产”

Codex Code Review rules 的关键价值不是让提示更长，而是把仓库里的高后果不变量写成可引用规则。对 AI Radar 来说，适合写进规则的是: `source-cards` 当日条数必须等于 `metrics.sourceCards`，`report-data.js` 必须和 JSON 同步，公开站点不得包含 cookie、截图、私信、通知、书签、密钥和本机私有路径。

2. 手机控制面必须定义冻结点

Remote 文章把 Queue/Steer 讲得很清楚: Queue 是安全默认，Steer 是正在走错方向时的纠偏。个人工作流里应加一条冻结线: 采集和写作阶段可以 Steer；验证、commit、push、deploy 阶段只允许 Queue 补充检查，不随意改主线。

3. 私有工具接入要先缩小边界，再提高便利

Secure MCP Tunnel 的重点不是“能连上”，而是 customer-run client、outbound-only、explicit destination 和 inspectable operation。对本地 Obsidian、脚本、浏览器、GitHub、Vercel 这类入口，默认应先做超市上架清单: 哪些工具能用、只能读什么、能不能写、日志放哪里、如何撤销。

4. 工具路由成为 agent 质量的核心

Agents SDK Tools 把工具分成 hosted OpenAI tools、local/runtime execution tools、function tools、agents as tools 和实验性 Codex tool。Tool search 解决“大工具面一次性塞给模型”的 token 和选择问题；Programmatic Tool Calling 解决循环、分支、并发和中间计算问题。高风险动作不要交给程序化批处理，应保留直接审批。

5. Web search 和 computer use 要分开治理

Web search 适合公开来源候选池；computer use 适合对真实界面做观察、点击、输入。日报采集默认只读公开网页；如果后续用 computer use 复核网页或站点，也只能检查公开页面，不把截图、登录态和本地窗口内容写入公开产物。

6. GitHub Agentic Workflows 给自然语言自动化补上工程外壳

GitHub 文档显示 agentic workflow 用 Markdown body 写自然语言任务，用 frontmatter 写触发、权限、网络和 safe outputs，再编译成 hardened Actions。这个形态适合把“每日状态报告”“CI 失败调查”“文档更新”“知识卡同步”从聊天任务变成仓库资产。

7. 多 agent 路由需要 engine、secret、timeout 和成本上限

GitHub Agentic Workflows 的 engine reference 显示同一 workflow 可选择 Copilot、Claude、OpenAI Codex、Gemini 等 coding agents。真正要沉淀的不是“哪个模型更强”，而是每个 engine 的 secret、版本、timeout、harness、预算和失败回退策略。

8. X 上真实案例的共同点是“上下文和验收比速度更值钱”

Pedro Pinera 的 Mastodon iOS/Codex/Tuist 迁移案例强调 agent 处理真实 Xcode 迁移反馈循环，并把经验写成 migration skill；Degen Sing 的一人 agent team 长帖强调 orchestrator、任务注册、监控、质量门和成本。两者共同指向: agent fleet 的瓶颈不是生成代码，而是任务边界、上下文、资源和验收。

### iPhone + Mac + Codex 协作玩法

今日推荐链路:

1. iPhone: 捕捉公开链接，启动或转向 Codex task；只写目标、禁止动作和成功标准。
2. Queue/Steer: 采集阶段发现遗漏可 Steer；验证/发布阶段新增检查用 Queue。
3. Mac/Codex: 执行文件写入、JSON/JS 同步、测试、commit、push、Vercel deploy。
4. `AGENTS.md`: 固化日报发布规则、公开来源边界、sourceCards/metrics 一致性。
5. Tool search/PTC: 只用于低风险去重、字段校验、聚合和格式检查；不可逆动作保留审批。
6. MCP/插件: 本地和私有工具只按白名单接入；不创建公网隧道。
7. 知识库: 每天只沉淀可复用操作资产，不把新闻摘要塞进长期记忆。

### 可沉淀知识卡片

#### 卡片 1: 入口冻结协议

- 概念: 把 agent 长任务分成可 Steer 阶段和冻结阶段；采集/探索可转向，验证/发布只补检查。
- 适用场景: iPhone Remote、每日自动化、长会话换车、发布链路。
- 操作步骤: 先声明阶段 -> 采集阶段允许纠偏 -> 进入验证后只 Queue 新检查 -> commit/deploy 后只处理失败原因 -> 输出证据。
- 风险: 发布阶段随意转向会制造半成品文件和难追踪 diff。
- 原文: https://developers.openai.com/blog/mastering-codex-remote-for-engineering

#### 卡片 2: 工具路由白名单

- 概念: 不把所有工具一次性交给模型，而是按任务加载、按风险授权、按输出验收。
- 适用场景: Agents SDK、source-card 去重、公开网页采集、MCP 工具组、本地脚本。
- 操作步骤: 工具按 namespace 分组 -> 低风险读操作可 tool search -> 批量聚合可 PTC -> 写操作需要审批 -> 输出进入 schema 校验。
- 风险: 大工具面会增加误调用概率；程序化调用不适合审批敏感动作。
- 原文: https://openai.github.io/openai-agents-python/tools/

#### 卡片 3: 私有工具窄通道

- 概念: 私有 MCP/内部 REST API 应通过 outbound-only、可检查、明确目的地的窄通道接入，而不是公开暴露。
- 适用场景: Obsidian、本地脚本、公司内网、个人数据工具、浏览器自动化。
- 操作步骤: 写上架清单 -> 限定目标/方法/路径/超时/响应大小 -> 本地 client 发起连接 -> 记录健康检查和日志 -> 定期撤销不用的入口。
- 风险: 隧道一旦变成通用网络桥，便利会吞掉安全边界。
- 原文: https://developers.openai.com/blog/connect-private-mcp-servers-to-openai-products

#### 卡片 4: 仓库化 agent workflow

- 概念: 重复自然语言自动化应进入仓库，用 frontmatter 定义触发、权限、网络、安全输出、预算和 engine。
- 适用场景: 每日晨报、仓库状态、CI 失败调查、issue triage、知识卡同步。
- 操作步骤: 写 workflow.md -> 声明只读默认和 safe outputs -> 设 engine/secret/timeout/budget -> 编译 lock workflow -> 手动触发验证。
- 风险: 没有 safe outputs 的 agent workflow 会把“自然语言任务”变成难审计写权限。
- 原文: https://docs.github.com/en/enterprise-cloud@latest/copilot/concepts/agents/about-github-agentic-workflows

## 白话版

今天这期可以理解成: 你不是在雇一个“很会写代码的人”，而是在搭一个小型工地。

iPhone 像工地对讲机。它适合说“先干 A”“别动 B”“发现方向错了马上停一下”。但真正看图纸、验收钢筋、签字交付，还是得回 Mac。尤其到了发布阶段，不要一边浇混凝土一边临时改楼层结构。

`AGENTS.md` 像贴在墙上的施工规范。不是写“请认真施工”，而是写“这根梁不能动”“公开网页不能出现私人物品”“日报 JSON 和 JS 必须一致”。Codex review 看到问题时，能指着墙上的规则说: 我按这条判断。

Tool search 像工具房管理员。以前是把所有工具一股脑堆到工人面前，现在是先问“你这步要拧螺丝还是刷墙”，再拿对应工具。Programmatic Tool Calling 像让同声传译帮你把十个库存表一起核对，但它不该替你签合同、付款、发布网站。

Secure MCP Tunnel 像仓库只开一扇只出不进的小门。里面的人拿着超市上架清单出去对接，外面的人不能随便冲进仓库翻东西。方便要有，但门禁也要有。

GitHub Agentic Workflows 像把每天口头交代的活写成正式值班表: 几点开始、谁能看、谁能写、预算多少、产物放哪、出错谁验收。这样以后换模型、换机器、换会话，也不会每次从零口述。

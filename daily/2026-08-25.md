### 今日结论

今日主线是: AI 工作台正在从“多入口能用”进入“迁移、审批、预算和知识库边界必须显式化”的阶段。OpenAI 在 8 月 24 日标记 `codex mcp-server` 命令废弃，推荐 Codex app server，并发布 Codex CLI 0.149.1；8 月 20/21 日的 ChatGPT 与 Codex 更新继续把 Apple Messages、Site 协作、Codex snapshot、插件发现、长会话加载和 iOS 附件放到同一产品面；OpenAI Cookbook 的 Responses API 单次预算控制把每个 agent run 的成本闸门写成可执行模式；GitHub Slack/Teams Copilot 则把团队聊天变成共享 agent 现场，并把预算、云沙箱和额外审批推到前台。

直接动作是: 后续个人工作流不要只问“这个入口能不能调 agent”，而要沉淀五类资产: Codex MCP Migration Card、Cross-App Send Approval、Run-Level Spend Gate、Shared Agent Budget Envelope、Second-Brain Vault Gate。iPhone/Remote 负责派工和审批提示；聊天入口只做共享可见性；Mac/Codex 仍负责文件、测试、diff、commit、push、deploy 和最终证据。

### Codex/GPT 工作流启发

1. `codex mcp-server` 被标记废弃，说明本地 MCP 入口不能长期按命令习惯固化；需要把“当前入口、替代入口、版本、依赖客户端”写进迁移卡。
2. Codex CLI 0.149.1 是最新稳定 release；自动化应记录采集日期和 release 页，不假设本机已升级。
3. 0.150 alpha 仍高频存在，适合观察方向，不适合把 alpha 行为写进生产闸门。
4. 8 月 20 日 Codex 0.149.0 的 agents dashboard、queue、doctor、config overrides 和 reasoning effort 仍是发布前证据面的核心资产。
5. Apple Messages plugin 能读搜消息并准备或发送信息，默认需要用户确认收件人与正文；这类能力必须保留逐次发送审批。
6. Site co-editing 让编辑者可读 live database data、更新、保存版本和发布变化；站点协作需要 owner、editor、publish 和 restoration 边界。
7. Codex snapshot 是静态只读分享，但官方仍提醒用户复核敏感内容；公开日报只可保留总结和公开链接，不带本地过程。
8. 插件发现和 universal plugin directory 让同一个插件可能出现在 Chat、Work、Codex、CLI；插件能力账本必须跨入口，而不是只按 app 名称记录。
9. Sign in with ChatGPT 不等于授权插件动作；连接身份、插件权限和动作审批是三层不同闸门。
10. 插件 hooks 会在生命周期点运行；启用前必须复核 hook 来源、命令、外部副作用和撤销路径。
11. OpenAI Cookbook 的 per-run spending controller 把“能否继续下一次模型调用”变成预算判断，而不是事后看账单。
12. 预算控制需要价格验证日期；`verified_at` 只证明何时查过价格，不证明今天仍然有效。
13. hosted tools、regional prices、background requests 和 storage 等费用可能不在模型 token 预算内；任务信封必须标注排除项。
14. Slack/Teams 共享 agent session 提高透明度，也放大多人 steering 和隐式改需求风险。
15. GitHub 在 Slack/Teams 两条线都强调额外审批和预算；聊天入口不是最终交付证据。
16. JetBrains enterprise managed settings 的插件治理、MCP allowlist、OpenTelemetry 和 permission modes 可借鉴为个人工作台控制矩阵。
17. Obsidian/Codex second brain 文章的共同点是: vault 只是文件夹，真正关键是最小 vault、敏感隔离、Git 历史、预览和回滚。
18. AI 知识库不应从“全库读写”开始；先跑一个小工作流和一个小 vault，再逐步扩权限。

### iPhone + Mac + Codex 协作玩法

今日推荐链路:

1. iPhone/Remote: 只发送任务信封，写清日期、目标、是否允许发布、是否允许消息发送和停止条件。
2. Chat: 把口语需求拆成入口、读写边界、预算、approval、公开边界和最终 owner。
3. Plugin/Codex intake: 先看是否涉及 deprecated MCP command、plugin hooks、connectors、MCP servers 或 Sign in with ChatGPT。
4. API run: 若调用 Responses API，先计 token、预留 worst-case 成本、记录价格验证日期和费用排除项。
5. Slack/Teams: 只做共享派工和可见 steering；写动作必须落到 issue/PR/Codex 本地验证。
6. Second brain: 新知识库自动化先用小 vault + Git + preview + rollback，不给全库全权限。
7. Mac/Codex: 发布前检查 repo 状态、source-card 数、JSON/JS 同步、diff、commit、push 和 Vercel Ready。

### 可沉淀知识卡片

#### 卡片 1: Codex MCP Migration Card

- 概念: 当 Codex 旧 MCP 命令废弃时，迁移不能靠记忆，要写成可复核卡片。
- 操作步骤:
  1. 记录旧命令、当前版本、使用场景和调用方。
  2. 记录替代入口，例如 Codex app server 或特定客户端插件。
  3. 标注涉及的 MCP server、transport、权限和 owner。
  4. 在小任务上验证新入口可读、可写、可停止、可回滚。
  5. 保留旧入口下线日期、失败症状和恢复路径。
- 风险: 命令习惯最容易变成隐性依赖；废弃后才发现会卡住自动化。

#### 卡片 2: Cross-App Send Approval

- 概念: Apple Messages、Sites、snapshots 等跨 app 能力必须把“准备、发送、分享、发布”拆成不同审批。
- 操作步骤:
  1. 区分 read/search、draft、send、share、publish 五类动作。
  2. 每次发送前复核收件人、正文、附件和是否含非公开信息。
  3. 默认使用 allow once，不给长期免审批。
  4. 分享 snapshot 前扫描本地路径、diff、截图、私有上下文和凭证形态。
  5. 发布后保留 commit/push/deploy/inspect 证据。
- 风险: 同一个插件同时能读和发，省一步审批就可能把私有过程发出去。

#### 卡片 3: Run-Level Spend Gate

- 概念: agent 一次任务要有自己的预算闸门，不能只靠组织或项目总额度。
- 操作步骤:
  1. 为每类任务设置 run budget、模型、service tier 和最大输入/输出 token。
  2. 请求前先 count tokens，并按 worst-case 输入价格和最大输出预留。
  3. 返回后校验模型、service tier、状态和 usage，再结算实际成本。
  4. 若请求中断、usage 缺失或费用无法确认，阻断该 run。
  5. 记录价格验证日期和预算排除项，例如 hosted tools、storage、regional prices。
- 风险: 多步 agent 最容易一小步一小步超支；没有预留机制就只能事后补救。

#### 卡片 4: Second-Brain Vault Gate

- 概念: Obsidian/Markdown 知识库接入 agent 前，先限制 vault、权限和回滚路径。
- 操作步骤:
  1. 从一个小 vault 和一个明确工作流开始。
  2. 把敏感笔记放在 agent 不可访问的 vault 或目录。
  3. 所有批量改写先走 preview/diff。
  4. 用 Git 或等价备份保存可回滚历史。
  5. 每次运行记录输入来源、改动范围、链接策略和人工复核结果。
- 风险: “本地文件”不等于“本地推理”；云 agent、同步插件和连接器都有各自边界。

## 白话版

今天这期像是“家里工具越来越多，终于要给每个插座、门禁和账本贴标签”。

Codex MCP server command deprecated 就像老门钥匙要退役。以前大家习惯从这把钥匙进门，现在官方说要换成 Codex app server 或对应插件。重点不是“换一条命令”这么简单，而是要知道谁还在用旧钥匙、换新钥匙后能不能开同一扇门、出问题怎么退回。

Apple Messages、Sites、Codex snapshot 像把厨房、客厅和门口快递柜都连到一个遥控器上。能读消息、草拟消息、发消息、协作改站点、分享快照，听起来很方便；但每个动作的风险不一样。读一下和发出去不是一回事，准备草稿和真正发送也不是一回事，所以要逐次确认。

Responses API 的 per-run spending controller 像出门前先给这趟车放 20 块油钱。每开下一段前先算够不够，不够就别硬上路。它提醒我们: agent 不是只花一次钱，多轮任务会一点点累加；价格还会变，所以“我上次查过”不等于今天仍然准确。

Slack 和 Teams 的 Copilot agent 像把施工现场搬进群聊。大家都能看、能插话、能改方向，很适合团队协作；但群聊不是验收台。真正能不能合并、能不能发布，还得看 PR、测试、审批和部署证据。

Obsidian second brain 则像让保洁阿姨进书房整理资料。正确做法不是一上来给全屋钥匙，而是先给一个小书架、明确整理规则、每次整理前后拍清单、东西乱了能恢复。知识库越值钱，越不能从全库全权限开始。

所以今天最该沉淀的不是某个新玩具，而是五张门禁卡: Codex MCP 迁移卡、跨 app 发送审批、单次任务预算闸门、共享 agent 预算信封、知识库 vault 闸门。

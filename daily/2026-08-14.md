## 官方严谨版

### 今日结论

2026-08-14 的主线是: agent 工作流正在从“哪个模型更强”进入“插件、权限、沙箱、记忆、成本和产出边界能不能统一治理”的阶段。OpenAI 的 Plugins in ChatGPT and Codex 文档把 plugin 明确定义为 skills、apps 和 app templates 的工作流包，并强调 plugin 不会绕过 app 权限、源系统权限、动作确认、sync 范围和 workspace role。GitHub 的 Agent Plugins 1.0 则把同一个方向推到跨客户端标准: 一个 plugin 可以同时携带 skills 和 MCP server 配置，并在 VS Code、Copilot CLI、Copilot app 和 SDK 中复用，但仍需要 managed settings、marketplace 控制和 MCP allowlist。

GitHub 近几天的 Copilot 更新继续补齐治理面: Agentic Workflows 的 safe outputs 和 issue intents 让自动化写入带上 rationale、confidence 和 review panel；per-model token breakdown 把 input、output、cache read、cache write 拆进 usage report；JetBrains 更新把 persistent memory、Ollama BYOK、Codex sessions debug logs、permission modes 和 skills 放到同一个 IDE surface；Gemini 3.7 Flash 上架 Copilot 则再次说明多模型入口会越来越常态化。对个人 Codex/ChatGPT 工作流来说，关键不是追每个新模型，而是先建立“插件上架清单、权限继承表、MCP 白名单、记忆范围闸、成本四分账、最终证据链”。

对 AI Radar 的直接结论是: 自动化日报可以继续只读采集，但每次使用插件、app、MCP、sidecar、BYOK 或本地模型前，都要写清它能读什么、能写什么、是否需要确认、是否继承源系统权限、是否可被用户/管理员关闭、最终由哪一个本地证据收口。iPhone/Remote 继续只做派工、状态和低风险转向；Mac/Codex 继续负责文件、测试、diff、commit、push、deploy；任何插件安装、模型选择、记忆命中或云端 agent 状态都不能替代最终验收。

### Codex/GPT 工作流启发

1. Plugin 是工作流包，不是权限通行证

OpenAI Help Center 明确 plugin 可以包含 skills、apps 和 app templates，但 app 的 role access、read/write actions、confirmation、sync、source boundaries 和源系统权限仍然生效。个人工作流要把 plugin 当成“能力包+权限包”的组合审查，而不是只看它能做什么。

2. Skills 与 apps 要分开验收

Skill 主要是可复用指令、提示和流程；app 连接外部数据和动作。一个 plugin 可能只有 skill，也可能依赖 app。日报自动化可以使用本地 skill 规范，但只要接入 Gmail、GitHub、Vercel、Notion 这类 app，就要额外检查读写动作和确认规则。

3. Agent Plugins 1.0 让技能包变成跨客户端资产

GitHub 的 Agent Plugins 1.0 把 `plugin.json`、`skills/` 和 `mcp.json` 标准化，客户端私有能力放到 namespaced directory。可复用动作是: 通用能力写进标准目录，Copilot/Codex/VS Code 特有能力放到客户端目录，避免重复维护。

4. MCP allowlist 要和 plugin 上架清单绑定

Plugin 可以携带 MCP server 配置，意味着“安装插件”可能同时引入工具入口。任何 MCP 都要记录 server URL/command/name、可用 tools、是否有写动作、是否联网、是否需要凭证、是否可禁用。

5. Safe outputs 是云端自动化的写入闸

GitHub Agentic Workflows 默认 read-only，并通过 safe outputs 进行受控写入。对个人自动化的启发是: 写日报、开 issue、发评论、改 label、创建 PR 都应有白名单对象和字段级边界，不让 agent 自由决定写哪里。

6. Rationale/confidence 适合低成本人工复核

GitHub Issues 的 agent automation controls 给 label、field、type、close、assignee 这类动作附带 rationale 和 confidence。个人工作流也可以给候选来源、知识卡片、交易计划、PR comment 设 confidence，低置信度不自动执行。

7. 成本报告要按模型和 token 类型归因

per-model token breakdown 把 input、output、cache read、cache write 和 AI credits 放在一起。日报类长任务应记录: 候选扫描、主编辑、校验、发布各用了什么模型；输出膨胀、缓存写入和 sidecar 重试分别消耗多少。

8. Memory 是范围化能力

Copilot memory 在 JetBrains 中跨 agent chat sessions 保留上下文，但仍需要 toggle 和设置入口。个人 Codex 记忆也要区分用户偏好、仓库事实、自动化运行状态和当天临时判断，避免旧状态污染当天发布。

9. 本地模型/BYOK 是边界选择，不是默认替换

Ollama as BYOK provider 适合本地开发环境中的低风险辅助，但公开发布、高后果判断、授权动作和最终验收仍要看证据链。BYOK 前必须记录 provider、model、数据去向、日志、账单和停用方式。

10. IDE surface 正在变成 agent 控制台

JetBrains 更新同时提到 MCP、terminal、customizations、cloud agents、diff editing、Codex sessions debug logs 和 permission modes。IDE 不再只是编辑器，而是一个能管理本地/云端/插件/模型/日志的 agent 控制台。

11. 多模型入口会继续增加

Gemini 3.7 Flash 进入 Copilot 的 VS Code、CLI、cloud agent、app、JetBrains、Xcode、Eclipse 等入口，说明模型选择会变成日常配置。个人流程不要把模型名写死在任务定义里，要写选择理由和回退边界。

12. ROI 与采用阶段要一起看

Copilot impact dashboard 开始把成本、工资假设、PR output 和 adoption phases 放在一起。个人效率工具也要看“多花的 agent 成本是否换来可验证产物”，不是只统计启动次数。

### iPhone + Mac + Codex 协作玩法

今日推荐链路:

1. iPhone/Remote: 派工、看状态、补充公开链接、批准低风险转向。
2. Chat: 判断任务是否需要 plugin/app/MCP/sidecar，并写任务边界。
3. Work: 做长研究和候选材料整理，不把草稿当发布证据。
4. Codex: 在 Mac 上写文件、跑校验、看 diff、commit、push、deploy。
5. Plugin 上架清单: 记录 skills、apps、app templates、role access、读写动作、确认要求。
6. MCP 白名单: 记录 server、tools、命令/URL、凭证、联网、写权限。
7. Memory 闸: 用户偏好跨项目，仓库事实留仓库，临时判断当天失效。
8. BYOK 闸: 先写 provider、model、数据去向、账单、日志、停用，再使用。
9. 成本闸: 按模型和 token 类型记录 input/output/cache read/cache write。
10. 验收闸: 只有本地文件、校验、diff、push、deploy 相称证据齐全才标完成。

### 可沉淀知识卡片

#### 卡片 1: Plugin 上架清单

- 概念: 每个 plugin 上线前记录 included skills、apps、app templates、源系统、读写动作、sync、role access、确认要求和试点范围。
- 适用场景: ChatGPT/Codex plugin、Copilot plugin、内部 MCP plugin、自建技能包。
- 操作步骤: 看 plugin manifest -> 列 skills/apps -> 查 app 权限 -> 查源系统权限 -> 设只读优先 -> 小范围烟测 -> 定期复核。
- 风险: plugin 可见不代表 app 可用；app 可用也不代表用户有源系统权限。
- 原文: https://help.openai.com/en/articles/20001256-plugins-in-codex/

#### 卡片 2: MCP 白名单

- 概念: 任何由 plugin 或配置带入的 MCP server，都要按 URL/command/name、tools、读写动作、凭证、网络、禁用路径建立白名单。
- 适用场景: Codex MCP、Agent Plugins 1.0、GitHub Copilot managed settings、内部工具服务器。
- 操作步骤: 列 server -> 列 tools -> 标读写 -> 查凭证和联网 -> 绑定 approved marketplace/plugin -> 记录禁用方式。
- 风险: 一个看似只是 skill 的插件，可能同时带入 MCP 工具入口。
- 原文: https://github.blog/changelog/2026-08-12-agent-plugins-1-0-in-vs-code-copilot-cli-and-the-copilot-app/

#### 卡片 3: Issue Intent 审批层

- 概念: issue 自动化写入 label、field、type、close、assignee 时，给每个动作附 rationale、confidence 和 review 状态。
- 适用场景: triage、metadata enrichment、spam detection、agentic workflows safe outputs。
- 操作步骤: 要求 action intent -> 高置信度可自动 -> 中低置信度进 review panel -> 搜索 `has:suggestions` -> 定期看误判。
- 风险: 审批面板是协作便利，不是服务端安全边界；真正边界仍是权限和 safe outputs。
- 原文: https://github.blog/changelog/2026-07-23-agent-automation-controls-in-github-issues-in-public-preview/

#### 卡片 4: 成本归因表

- 概念: agent 成本按模型和 token 类型拆成 input、output、cache read、cache write、AI credits，并关联产物数量或质量。
- 适用场景: 日报、PR review、长研究、sidecar 扫描、企业 Copilot adoption、个人 Codex 自动化。
- 操作步骤: 记录模型 -> 拆 token 类型 -> 关联任务阶段 -> 标记重试/sidecar -> 对照产物 -> 每周删除低 ROI 流程。
- 风险: 只看总费用会掩盖输出膨胀、缓存写入和低价值重试。
- 原文: https://github.blog/changelog/2026-08-11-per-model-token-breakdown-in-the-usage-report/

## 白话版

今天这期像是在给 AI 工作台做“超市上架清单”。

以前我们看到一个插件，会想: 这个东西能帮我干啥？现在要多问几句: 它里面装的是说明书、工具，还是外部系统钥匙？它能不能读资料？能不能写东西？写之前要不要问我？它是不是继承了公司权限？用户在源系统里没权限的东西，它会不会越权拿到？

OpenAI 的 plugin 文档像超市管理制度: plugin 是一个货架包，里面可以有 skills、apps 和 app templates。Skill 像说明书，告诉 Codex 怎么干活；app 像连接外部仓库、邮箱、CRM 的通道；app template 像还没装好的货架，需要管理员先配置。货架上看得到，不代表你能拿；你能拿，也不代表能直接带出门。

GitHub 的 Agent Plugins 1.0 像统一包装规格。以前同一个工具要给不同商店分别换包装，现在可以用一套盒子装 skills 和 MCP server。好处是省重复维护；风险是盒子里可能不只有说明书，还可能有真正能操作外部系统的工具。所以 MCP 也要进白名单，像超市上架清单一样写清楚: 这是什么货、从哪里来、谁能用、能不能带出门、出了问题怎么下架。

成本这边也在变细。per-model token breakdown 像账单终于不只写“本月花了 100 元”，而是写清楚: 哪辆车花的油、进货花了多少、送货花了多少、ETC 缓存读写花了多少。以后看 agent 不是看“用没用”，而是看“花的钱有没有换来可验证产物”。

所以今天的关键词不是插件多，而是上架前要验货。能重复用的能力值得沉淀，但每个能力都要贴清标签: 权限、数据、动作、记忆、成本、下架方式和最终验收证据。

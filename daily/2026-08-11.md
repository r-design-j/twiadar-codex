### 今日结论

2026-08-11 的主线是: 高能力 agent 正在从“帮我做事”进入“被授权、被隔离、被计量、被复核”的生产阶段。OpenAI 8 月 10 日在 ChatGPT & Codex changelog 中把 Daybreak 拆成 Blue/Red 两级访问，强调经批准身份、workspace/API organization、项目、模型和产品表面才是可用边界；同一页 8 月 7 日的 Codex CLI 0.147.0 把 Agent Plugins、长会话分段、`--approve-for-me`、MCP 2026-07-28 支持和 secret redaction 放进 CLI 主线；ChatGPT release notes 则在 8 月 7 日让 Voice 支持文件和 Projects，8 月 6 日把 GPT-5.6 Sol/Luna 更新限定在 Chat 体验，不影响 Work/Codex。

这几条放在一起看，重点不是“又有一个模型/插件/入口”，而是每个入口都要标注职责: Voice 可以带文件和 Project 上下文，但仍是控制面；Codex CLI 可以自动复核部分审批，但必须配合 sandbox、permission profile 和 auto-review；Daybreak Blue/Red 提醒高风险能力必须有已批准的身份、范围、日志和人类复核；GitHub 的 Copilot app、metrics dashboard、AI credit pools 和 harness 文章也在讲同一件事: agent 规模化以后，成本、权限、项目上下文、并行会话、PR 验收和采用阶段都要可观察。

对个人 AI Radar 的直接启发是: iPhone/Remote/Voice 继续只做派工、状态、低风险审批和转向；Mac/Codex 负责本地文件、测试、diff、commit、push、deploy；Chat/Work 负责判断、研究、报告和 Project 上下文；任何“自动批准”都只能进白名单场景；任何高权限插件或安全工作流都要先写清 scope、reviewer、sandbox、credit/budget、日志和退出条件。

### Codex/GPT 工作流启发

1. Daybreak Blue/Red 是高权限 agent 的权限模型样板

安全场景只是最尖锐的例子。任何高能力 agent 都应复制同一套边界: 谁被批准、在哪个 workspace/API organization、哪个项目、哪个模型、哪个产品表面、能做什么、谁复核、日志在哪里。

2. `--approve-for-me` 不是“自动放行所有命令”

Codex CLI 0.147.0 的自动复核审批要和 permission profile、sandbox、auto-review 绑定使用。适合低风险、可回滚、可重复的命令，不适合未知脚本、外部写动作、凭证处理、发帖、支付或生产变更。

3. Agent Plugins 进入目录后，插件治理要前置

插件可搜索、可携带、可跨本地/个人/workspace/远程目录出现，意味着“看得见”不等于“能安全用”。启用前要有来源、依赖 app、读写动作、审批门、网络策略、同步范围和回滚路径。

4. 长会话分段浏览要服务于收口

持久 sections 和长 transcript 分段不是为了无限开会，而是让长任务能按“目标 -> 执行 -> 验证 -> 决策 -> 交接”切块。每段必须有状态、证据和下一步，否则只是更长的上下文负债。

5. Voice + Projects 让移动/语音入口更有上下文，但不改变职责

Voice 能上传文件、引用 Project chats/sources/instructions，适合临时问数、补充材料、口头转向。最终完成仍取决于本地文件、测试、diff、push 和 deploy 证据。

6. Chat 模型更新不能直接外推到 Work/Codex

OpenAI release notes 明确 8 月 6 日 GPT-5.6 Chat 更新不改变 Work/Codex。评估模型变化时要按产品表面拆开，不要把 Chat 体验的能力或限制直接套到 Codex 自动化上。

7. `AGENTS.md` 应写 review 规则，不只写编码偏好

OpenAI 的 Codex Code Review 规则文章说明，最有价值的是兼容性、数据边界、不可破坏协议、客户可见行为这类 reviewer 反复解释的判断。格式化和机械检查继续交给 CI。

8. 私有 MCP 应优先选择“边界显式”的连接方式

OpenAI 私有 MCP tunnel 的要点不是打洞，而是让客户侧 tunnel client、OpenAI-hosted endpoint、私有服务可达范围、健康检查和日志可解释。公开日报不能用公共 tunnel 暴露本地私有服务。

9. GitHub Copilot app 显示了 agent 桌面工作台的自然形态

Project 绑定上下文，多 session 分开推进，canvas 预览 UI，Agent Merge 跟 PR/CI/review。这和个人 Codex 工作流对应: 每个任务要有项目、线程、视觉/运行验收和合并出口。

10. 指标开始从“活跃人数”转向“采用阶段”

GitHub metrics dashboard 按 Code-first、Agent-first、Multi-agent/Copilot app 和 Passive 分组。个人也可以照抄: 记录自己哪些工作只是问答，哪些交给 agent 执行，哪些已经多 agent 化。

11. AI credit pools 把 agent 成本变成工程边界

成本池和预算不是财务才关心。长任务、并行 agent、自动 review、MCP 工具调用都需要预算停止条件。没有预算的自动化容易把“提效”变成不可见消耗。

12. GitHub harness 文章的反常识是: 先学工作台，再追插件

真正提升来自熟悉一个稳定 harness 的 prototype、plan、implement、review、sandbox、prompt caching 和成本策略；MCP、skills、custom agents 是进阶增强，不是起步条件。

### iPhone + Mac + Codex 协作玩法

今日推荐链路:

1. iPhone/Remote: 只做提醒、派工、状态查看、低风险审批和转向。
2. Voice: 用文件和 Project 上下文补充口头输入，但不批准高风险写动作。
3. Chat: 快速判断来源价值，冻结任务胶囊和公开边界。
4. Work/Projects: 组织长研究、资料源和报告草稿。
5. Codex CLI/App: 在本地仓库执行文件写入、测试、diff、commit、push、deploy。
6. Agent Plugins: 启用前走插件权限上架单。
7. MCP: 私有服务只走明确边界的本地/企业通道，不把本地服务暴露成公网入口。
8. Code Review: 用 `AGENTS.md` 记录高后果 review 规则。
9. Metrics: 每周记录 Chat-only、Agent-first、Multi-agent 和 Published 四类工作。
10. Budget: 长任务写明 token/credit/时间停止条件。

### 可沉淀知识卡片

#### 卡片 1: 高权限 agent 授权单

- 概念: 高权限 agent 先确认身份、workspace/API organization、项目、模型、产品表面、scope、reviewer、sandbox 和日志，再执行。
- 适用场景: 安全扫描、生产修复、外部写动作、批量自动化、插件启用。
- 操作步骤: 写任务目标 -> 写允许范围 -> 指定 reviewer -> 配 sandbox/permission profile -> 设置 auto-review/approval -> 执行后保存证据。
- 风险: 只写“用于防御/内部使用”不够，缺少身份和范围会让授权不可审计。
- 原文: https://learn.chatgpt.com/docs/changelog

#### 卡片 2: 自动审批白名单

- 概念: 自动审批只适合低风险、可重复、可回滚、已知命令；默认不覆盖外部写入、凭证、公开发布和生产变更。
- 适用场景: lint、format、unit test、只读检查、固定路径构建。
- 操作步骤: 列命令白名单 -> 绑定工作目录 -> 限制网络/写权限 -> 设失败停止 -> 每次记录命令和结果。
- 风险: 自动审批范围过大，会把“省一次确认”变成“失去安全边界”。
- 原文: https://developers.openai.com/codex/changelog

#### 卡片 3: Project/Voice 上下文闸

- 概念: Voice 可以带文件和 Project 上下文，但它是输入和控制入口，不是最终完成证据。
- 适用场景: 移动端补充材料、语音问答、长项目中途转向、跨设备继续。
- 操作步骤: 用 Voice 提供材料 -> 标注 Project 来源 -> 生成任务胶囊 -> Mac/Codex 执行 -> 用测试/diff/deploy 收口。
- 风险: 把口头说明当作验收，会跳过本地证据。
- 原文: https://help.openai.com/en/articles/6825453-chatgpt-release-notes

#### 卡片 4: Harness-first 工作流

- 概念: 先掌握一个稳定 agent harness 的 prototype、plan、implement、review、sandbox、cost loop，再引入插件和 MCP。
- 适用场景: 新功能探索、UI 原型、代码改造、PR review、个人 agent 编队。
- 操作步骤: 选固定工具 -> 原型探索 -> 计划拆分 -> 执行实现 -> 运行测试 -> 审 diff -> 记录成本/耗时。
- 风险: 先追插件会让工作流碎片化，反而增加上下文和验收成本。
- 原文: https://github.blog/ai-and-ml/github-copilot/the-harness-is-all-you-need-mostly/

## 白话版

今天这期像是在给一间 AI 工厂重新上保险。

以前我们关心的是“这个 agent 会不会干活”。现在真正的问题变成: 谁把钥匙给了它、它能进哪间屋、能不能联网、能不能动生产线、花多少钱、干完有没有小票。

Daybreak Blue/Red 像两种安全通行证。Blue 是普通防御工作，Red 是更高风险的红队/验证工作。不是你说“我是防御用途”就能进，必须写清楚哪个人、哪个组织、哪个项目、哪个模型、哪个界面被批准。这个规则虽然来自安全场景，但适合所有高权限 agent。

Codex CLI 0.147.0 像车间升级了工具柜: 插件能进目录，长会话能分柜子收纳，部分审批能自动复核，MCP 协议也更新了。但工具柜越高级，越要有白名单。`--approve-for-me` 不是把所有门都打开，而是只让熟悉、低风险、可回滚的动作走快速通道。

Voice 支持文件和 Projects，像你可以拿着资料对着对讲机说“帮我看这个项目”。但对讲机仍然不是验收员。它能帮你描述、补材料、转方向，最后还得 Mac/Codex 去跑测试、看 diff、push、deploy。

GitHub 的 Copilot app 和 harness 文章也在说类似的话: 先别追每个新插件，先学会一个稳定工作台。先做原型，再做计划，再实现，再 review，再看成本。就像开车先熟悉方向盘、刹车和仪表盘，别一上来就装一堆外挂。

所以今天的关键词不是“更强”，而是“更有边界”。AI 工厂可以越来越自动，但每台机器都要贴标签: 谁能开、能开多久、能干什么、出了问题谁看、完工小票在哪里。

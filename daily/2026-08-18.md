### Codex/GPT 工作流启发

1. Codex SDK 的价值不是“再多一个 API”，而是让外部系统能标准化创建 Cloud tasks，并读取任务结果。对个人自动化来说，API 请求返回只能证明任务已进入执行面；完成仍要看文件、测试、commit、push、deploy 或平台输出。
2. Codex 0.141.0 的重点在执行器可靠性: 远程执行通道加密、跨平台保留 executor-native cwd/shell、插件 MCP 可按线程激活。这说明远程 Codex 不是简单云端 shell，必须把执行器、目录、shell、插件和权限写进证据链。
3. `wait_agent` 可被 steer interrupt 这类能力，适合长任务中途改方向，但也带来验收风险。每次中断后要记录“旧任务是否关闭、哪些输出被接受、哪些未接受”，不能让半截 sidecar 输出混入最终结论。
4. GitHub Agentic Workflows 把自然语言 workflow 文件编译成 hardened Actions workflow。它的关键不是省 YAML，而是 frontmatter 里的 trigger、permissions、engine、network、tools、safe-outputs 成为可审计合同。
5. Safe outputs 是写动作隔离层: agent 可以读、分析和产出结构化请求，但创建 issue/comment/PR 等动作由后续权限控制 job 执行。这比把 `issues: write` 直接交给 agent 更适合自动化。
6. Issue intents 给 label、field、type、close、assignee 这类 issue 变更附上 rationale 和 confidence。对高频 triage 来说，低置信度变更应默认进入审批面，而不是直接写仓库状态。
7. ChatGPT desktop app 合并 Chat、Work、Codex 后，入口更顺手，但完成证据更容易混。Chat 的判断、Work 的文档、Codex 的 repo diff 和终端输出必须分开标注。
8. Slack Agents 把 agent 放进真实团队频道，能力更强，风险也更现实。只要 agent 使用 shared auth，就要优先问: 这是谁的账号、能访问哪些系统、谁能触发、失败会发到哪里。
9. Claude Code subagents/hook 文档提供了一个外部参照: 探索型子代理应只读，执行型子代理要限制工具、权限、hooks 和记忆。Codex/Luna/DS 的路由也应保持同样的边界意识。
10. Obsidian Web Clipper 仍适合作 source-card 工厂，但今天更适合升级模板: 除 URL/作者/摘要外，增加 evidence_type、action_surface、write_risk、reuse_asset 四个字段。

### iPhone + Mac + Codex 协作玩法

今日推荐链路:

1. iPhone/Remote: 发起任务，只写目标、公开边界、低风险转向和是否允许发布。
2. Chat: 冻结今日主题、Top 5、证据等级和不做事项。
3. Codex SDK/API 层: 对可 API 化的重复任务，用 Task API Envelope 固定 prompt、repo/ref、权限和回传字段。
4. Luna/只读侧车: 只读扫描公开候选源，只回传 JSONL，不写文件。
5. Mac/Codex: 写 daily、source-cards、knowledge、site data，并保留本地验证证据。
6. GitHub Agentic Workflows: 若未来迁移 triage/report，写动作只能走 safe outputs。
7. Slack/桌面: 只作为触达和协作入口，不作为发布完成证据。
8. 回看: 只报告日报路径、摘要、Top 3 链接、GitHub URL、网站 URL 和待拍板事项。

### 可沉淀知识卡片

#### 卡片 1: Codex Task API Envelope

- 概念: 外部系统触发 Codex/Cloud task 时，必须把 API 请求、执行边界和完成证据拆开记录。
- 操作步骤:
  1. 写清触发系统、task 名称、目标和输入 prompt。
  2. 写清 repo/ref、允许读取、允许写入、禁止动作和审批动作。
  3. 写清模型/推理档位、工具、插件和连接器。
  4. 写清回传字段: status、artifact、diff、log、error、review item。
  5. 写清本地或平台验收命令。
  6. 结束后记录 task id、最终状态、commit/deploy/PR/issue URL。
- 风险: API accepted 或 task queued 不是完成证据；它只证明任务进入执行队列。

#### 卡片 2: Remote Executor Evidence

- 概念: 远程执行器要像真实工作台一样记录环境，而不是只记录一句“远程跑了”。
- 操作步骤:
  1. 记录 executor 类型、宿主、工作目录和 shell。
  2. 记录 sandbox、network、plugin MCP、凭证来源和审批规则。
  3. 记录启动、interrupt、timeout、resume 和 close。
  4. 保留关键命令、测试、diff、commit、push、deploy 证据。
  5. 中断后标注接受/拒绝哪些输出。
  6. 失败时保留最后一次可验证状态，不破坏性重试。
- 风险: 跨平台路径、shell 和插件不同，可能让同一任务在本地和远程结果不一致。

#### 卡片 3: Safe Output Gate

- 概念: agent 不直接拿写权限；它输出结构化请求，由受控 job 执行声明过的写动作。
- 操作步骤:
  1. 在 workflow frontmatter 声明 trigger、permissions、engine、tools 和 network。
  2. 默认 read-only，写动作只列入 safe-outputs。
  3. 为 create-issue、add-comment、create-pr 等动作设置 max、labels、allowed fields。
  4. 对 issue 变更启用 rationale/confidence 或强制 issue intent。
  5. 低置信度或高影响动作进入审批面。
  6. 用 outcome 记录写动作之后的真实仓库状态。
- 风险: safe output 只证明动作被受控执行，不证明它被团队采纳或产生业务结果。

#### 卡片 4: 桌面/Slack/仓库三入口收口表

- 概念: ChatGPT desktop、Slack agent、GitHub/Codex repo 是三个入口，不是同一个完成面。
- 操作步骤:
  1. Chat/desktop 负责快速判断、启动和回看。
  2. Work 负责文档、表格、报告、Sites 等成品草稿。
  3. Slack 负责团队频道触达和协作，但 shared auth 单独审查。
  4. Codex/GitHub 负责 repo diff、测试、PR、commit、push、deploy。
  5. 每次任务记录入口、执行面、写动作面、最终证据面。
  6. 最终回报只说已验证证据，不把“可见消息”当“已完成”。
- 风险: 入口合并会降低启动成本，也会放大“看见了”和“做完了”的混淆。

## 白话版

今天这期像是从“派一个人去跑腿”升级到“开一个有门禁、有小票、有出入口登记的自动化流水线”。

以前你说一句话，agent 去做事。现在更像仓库发货: 订单从 API 进来，仓库工人只能在指定区域拿货，打包动作要走扫码台，出库小票要留下，快递到了没有还要看签收，不是“订单已创建”就算送到。

Codex SDK 像订单入口；Codex 远程执行器像异地仓库；GitHub safe outputs 像只能扫码出库的写动作闸门；Slack agents 像把工人拉进公司群，但谁的门禁卡给它用，必须写清楚；新 ChatGPT 桌面 app 像把前台、办公室和施工间放到一栋楼里，方便是方便，但验收还是得去施工间看文件、测试和发布结果。

所以今天的结论很简单: agent 越能跨桌面、Slack、GitHub 和远程机器干活，越不能只看“它说做了”。要看任务单、权限单、写动作闸门和最后小票。

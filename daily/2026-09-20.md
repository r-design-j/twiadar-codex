### Codex/GPT 工作流启发

1. SDK release 不再只是模型调用接口更新，而是可能新增凭证、存储、安全事件和媒体安全管理面。
2. OpenAI Node 7.20.0 的 vault credentials 和 external storage configuration 需要独立 owner、环境和回读记录。
3. safety warning / deactivation webhook events 表明安全状态也会走事件流，不能只看普通成功/失败响应。
4. SIP media security 进入 incoming call events 后，实时语音/电话场景要把媒体安全状态写进验收。
5. Codex alpha 连续滚动到 0.156.0-alpha.9，但 release body 稀疏，适合观察趋势，不适合当默认升级依据。

7. Claude Code 2.1.278 把 auto mode classifier 移到 server-side 的默认路径，成本归因要重新看。
8. 自动路由必须记录 classifier 在哪里跑、是否 fallback、fallback 是否收费、状态页如何显示。
9. Agents Python 0.22.3 的 conditional approvals 修复提醒: 审批应绑定验证后的工具参数，而不是原始意图文本。

12. tracing 不缓存缺失的 OPENAI_API_KEY，可以避免一次环境缺失污染后续修复后的运行。

### 可沉淀知识卡片

#### 卡片 1: SDK Operations Surface Register

- 概念: 把 SDK 新增的 vault、external storage、safety case、webhook event 和 SIP security 当成运营面变更，而不是普通类型更新。
- 使用场景: SDK OPS
- 操作步骤:
  1. 记录每个新增 API 面的 owner、权限、环境、事件类型和回读命令。
  2. 把 vault credentials、external storage、safety case、webhook events 和 SIP media security 分成独立验收项。
  3. 升级后先跑只读 inventory，再决定是否允许创建、更新或删除远端配置。
  4. 公开报告只保留来源链接和总结，不写凭证名、端点细节或本地路径。
- 风险: SDK release 可能打开新的管理入口；只跑 import 会漏掉权限和外部事件风险。

#### 卡片 2: Alpha Churn Observation Lane

- 概念: 快速滚动的 alpha 版本先进入观察 lane，用来判断方向，不自动替换稳定默认。
- 使用场景: CODEX RUNTIME
- 操作步骤:
  1. 记录 alpha tag、发布时间、是否有完整 release body 和相邻稳定版。
  2. 只有出现明确修复、功能说明或本地问题匹配时，才开 disposable workspace smoke。
  3. 把 alpha 结果和 stable 结果分栏保存，禁止混写成同一条通过证据。
  4. 如果 release body 稀疏，只能写“观察”，不能写“建议升级”。
- 风险: alpha 连续发版可能代表活跃，也可能代表不稳定；没有差异证据时不应推广。

#### 卡片 3: Server-Side Auto Classifier Receipt

- 概念: 自动路由要记录分类发生在哪里、是否计费、状态页如何显示，以及如何退出。
- 使用场景: ROUTING COST
- 操作步骤:
  1. 记录 provider、gateway、auto classifier location、status output 和 opt-out flag。
  2. 如果 fallback 会计费，把 billed fallback warning 单独写进成本风险。
  3. 比较模型效果前，先确认分类开销是否由客户端、服务端或供应商承担。
  4. 对企业/网关环境保留一次状态读回，避免把路由变化误判成模型变好或变差。
- 风险: 自动模式如果不记分类位置，会让成本、延迟和质量归因全部混在一起。

#### 卡片 4: Agent Runtime Recovery Smoke

- 概念: 代理 SDK 升级要验证恢复、审批、会话存储、工具记账和子进程清理。
- 使用场景: AGENT RUNTIME
- 操作步骤:
  1. 准备一个会触发 conditional approval、tool-not-found、resume 和 tool usage 的 fixture。
  2. 用并发 async SQLite 启动检查 session 初始化是否稳定。
  3. 验证 shell/apply_patch 等工具调用能进入 session usage ledger。
  4. 中断 stream 后检查子进程是否回收，并记录退出码。
- 风险: 长任务最怕表面恢复成功，实际漏记工具、丢失输出或留下后台进程。

#### 卡片 5: Feature Engagement Adoption Lens

- 概念: 看 AI 工具 adoption 不只看席位和活跃人数，还要看具体功能、技能和自定义项有没有被真实使用。
- 使用场景: ADOPTION METRICS
- 操作步骤:
  1. 把 seat count、active users、feature engagement 和 customizations usage 分开。
  2. 按 review、agent host、CLI、MCP、slash command、plugin 等 surface 归类。
  3. plugin totals 是 skill totals 子集时不要重复相加。
  4. 用数据决定培训和模板投入，而不是只看授权是否打开。
- 风险: 只看“有多少人开通”会把访问权限误认为工作流成熟。

## 白话版

今天的 AI 工具像办公室从“多了几个聪明同事”，升级成“多了几扇新门、几把新钥匙、一个自动分派台和一块考勤屏”。

第一，OpenAI Node 7.20.0 像把钥匙柜、外部仓库、安全告警和电话线路安检都接进 SDK。它不是普通工具箱多一把螺丝刀，而是多了几扇能影响真实系统的门，所以要先登记、再验门牌、最后才考虑能不能开。

第二，Codex alpha 快速跑到 0.156.0-alpha.9，像测试车一天换好几个小版本。能看方向，但不能直接拿来当通勤车；稳定线还是 0.155.1。

第三，Claude Code 的 auto mode server classifier 像把“该派哪辆车”交给调度中心判断，还会提示某些备用路线可能收费。比较模型前，先弄清楚调度费、油费和路线是谁算的。

第四，Agents Python 0.22.3 修的是长任务的地基：审批有没有绑到真正参数、断线后能不能续、SQLite 会不会抢锁、工具有没有记账、后台进程有没有收干净。白话说，不只是能不能跑，是摔一跤后能不能站起来并说清楚刚才发生了什么。

第五，GitHub 的 Copilot dashboard 和 CLI metrics 让“AI 工具有没有用起来”更像看健身记录：不能只看办了卡，还要看来了几次、练了哪些器械、有没有形成固定动作。

今天最值得带走的一句话: AI 工具越靠近真实工作台，越要给每一扇门、每一次自动分派、每一个恢复动作留小票。

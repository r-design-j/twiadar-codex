### 今日结论

2026-07-30 的主线是: agent 工作流正在从“能被远程启动和并行执行”进入“可被身份、工具、评审、指标和改进闭环治理”的阶段。OpenAI 的 ChatGPT Release Notes 在 7 月 29 日加入 Sign in with ChatGPT，降低插件和合作站点的账号接入摩擦；OpenAI Presence 把 voice/chat agent 的生产运行拆成岗位、权限、模拟、评估、升级和 Codex 改进建议；GitHub 则在 7 月 29 日把 code review 中的 agent skills 和 MCP 推到 GA，并让模型默认启用策略进入企业治理窗口。

### Codex/GPT 工作流启发

1. Sign in with ChatGPT 会降低插件接入门槛，也会放大授权复核的重要性

OpenAI Release Notes 显示 Sign in with ChatGPT beta 正从 Airtable、GitLab、HubSpot、Notion、Supabase、Vercel 等合作站点开始。它让账号创建和连接更顺，但“登录”不等于“工具权限已安全”。每个插件仍要单独复核能读什么、能写什么、是否会公开发布、是否会把上下文带到第三方。

2. Presence 把 agent 从“会回答”推进到“可生产运行”

Presence 的关键不是一个新聊天模型，而是把岗位、知识范围、系统访问、批准动作、升级规则、模拟、评估和上线后改进放到同一套产品里。对个人自动化来说，这意味着日报 agent 也要有线上信号: source-card 数量、链接可回溯、网站日期、Vercel Ready、失败原因和下次修正规则。

3. Codex 改进闭环正在变成生产 agent 的标准件

OpenAI Presence 描述的方式是: 线上会话、升级和质量信号暴露缺口，Codex 用 Presence plugin 调查并建议更新，团队测试后批准受控发布。个人工作流可以照搬: 自动化失败 -> Codex 查明原因 -> 产出补丁和验证证据 -> 人类确认是否发布 -> 写回 knowledge。

4. GitHub code review 的 skills/MCP GA 说明“评审上下文”正在资产化

GitHub code review 现在可用 agent skills 调用团队内部标准，并通过 MCP 拉取 issue tracker、文档系统、service catalog 等上下文，且 MCP tool call 限制为只读。可复用点是: 规则不应只在人的脑子里，也不应只写在聊天里；应变成仓库可读、可版本化、可归因的评审材料。

5. 模型默认启用策略需要单独治理

GitHub 的默认模型启用策略将在 8 月 26 日生效，未显式配置的 GA 模型会继承组织策略；显式选择保留，open-weight 或不在数据保留协议内的模型被排除。这给 Codex/ChatGPT 插件也提供了类比: 新能力不要默认混进生产链路，至少要有默认继承、显式允许、显式禁止、例外排除四种状态。

6. Usage metrics 正在从“有没有用”转向“谁在用、产出了什么”

GitHub 7 月 28 日更新把 Copilot app usage 扩展到 enterprise/user/org report rollups，包含 session、request、prompt、token、code activity、lines added/deleted 等字段。个人 AI Radar 也应避免只记录“今天跑了”；要记录 sourceCards、signals、knowledgeCards、验证命令、commit、deployment 和失败边界。

7. Agents SDK 工具层提醒我们把本地执行和模型请求分开

Agents SDK 文档把 hosted tools、computer use、shell、apply_patch、sandbox filesystem、skills、memory 等分层。工具调用由模型请求，但真正执行发生在应用或沙箱环境里。对 Codex 使用者来说，安全边界应写在执行环境、审批和文件权限里，而不是只靠 prompt 说“不要乱来”。

8. 企业工具选择正在从“买一个套件”变成“组合可观测工具”

Business Insider 报道 Disney 在美国将放弃 GitHub Copilot 等工具并准备采用 OpenAI Codex，同时保留 Claude Enterprise 和 Cursor。这个信号的价值不在于照抄 Disney，而是说明企业会用真实使用率、代码复杂度、清理成本、速度和 dashboard 重新组合工具。

### iPhone + Mac + Codex 协作玩法

今日推荐链路:

1. iPhone / Voice: 收集公开链接、口述候选选题、看长任务状态、批准低风险继续。
2. ChatGPT Sign-in / Plugin Directory: 接入 GitLab、Notion、Vercel 等工具前，先走身份披露和权限复核。
3. Codex on Mac: 执行本地文件更新、source-card 归一化、JSON/JS 同步、静态检查和发布。
4. GitHub PR / Review: 把仓库规则、MCP 上下文和 reviewer memory 放进可归因评论，不让规则只留在聊天里。
5. Metrics: 记录 sourceCards、signals、knowledge、commit、Vercel deployment、失败停点。
6. Knowledge: 把“可复用 agent 生产闭环”和“模型默认启用审计表”写回月度知识卡片。

### 可沉淀知识卡片

#### 卡片 1: Agent 生产闭环

- 概念: 生产 agent 不是 prompt，而是岗位、权限、模拟、评估、线上信号、改进建议和批准发布的闭环。
- 适用场景: Presence、日报自动化、客服 agent、研究 agent、代码 review agent。
- 操作步骤: 定义岗位 -> 限定知识/系统访问 -> 写批准和升级规则 -> 做模拟/评估 -> 收集线上信号 -> Codex 产出改进 -> 人类测试并批准。
- 风险: 只看“回答是否聪明”会漏掉权限、升级和上线后漂移。
- 原文: https://openai.com/index/introducing-openai-presence/

#### 卡片 2: 插件身份最小披露清单

- 概念: Sign in with ChatGPT 降低账号接入摩擦，但每个插件仍要单独审查身份字段、读写范围、公开动作和撤销路径。
- 适用场景: Airtable、GitLab、HubSpot、Notion、Supabase、Vercel 等插件/合作站点登录。
- 操作步骤: 确认共享字段 -> 查看插件权限 -> 区分读/写/发布 -> 标注是否进入公开产物 -> 记录撤销入口。
- 风险: 把登录便利误认为授权安全，会让低摩擦入口绕过原有审批。
- 原文: https://help.openai.com/en/articles/6825453-release-notes

#### 卡片 3: Review Skills + 只读 MCP

- 概念: 代码评审应能读取仓库规则和外部上下文，但外部工具调用默认只读，评论需要标明规则/MCP 来源。
- 适用场景: GitHub Copilot code review、Codex review、PR 评论、设计系统治理。
- 操作步骤: 写 `.github/skills/<skill>/SKILL.md` 或同类规则 -> 配置只读 MCP -> review 评论标注来源 -> 按误报/漏报更新规则。
- 风险: 评审工具有写权限会把“查证”变成“代操作”；规则无归因会难以迭代。
- 原文: https://github.blog/changelog/2026-07-29-copilot-code-review-agent-skills-and-mcp-now-generally-available/

#### 卡片 4: 模型默认启用审计表

- 概念: 新 GA 模型默认可用会提升速度，也会让未经评估的模型进入生产路径；需要默认继承、显式启用、显式禁用和例外排除四类状态。
- 适用场景: GitHub Copilot、Codex、ChatGPT Work、Claude、Cursor、多模型路由。
- 操作步骤: 列模型 -> 标数据保留/地区/成本/能力 -> 标启用状态 -> 设生效日期 -> 发布前跑代表任务。
- 风险: 新模型自动进入生产后，成本、合规、输出风格和回归可能同时变化。
- 原文: https://github.blog/changelog/2026-07-29-default-model-enablement-for-copilot-business-and-enterprise/

## 白话版

今天的变化像是公司终于不只是在问“这个员工聪不聪明”，而是在搭一套真正的上班制度: 谁负责哪个岗位，谁能进哪个系统，什么事要请示，出错以后谁看录像、谁改流程、谁批准上线。

Sign in with ChatGPT 像给很多合作工具开了一张统一门禁卡。进门更快了，但门禁卡不是万能钥匙。每次进 Notion、GitLab、Vercel 这类地方，还是要看它到底要你的名字邮箱，还是还想读项目、改文件、发到公网。

Presence 像把“AI 客服/AI 助手”从临时工变成正式岗位。正式岗位不只看它会不会说话，还要有岗位说明、操作手册、越权报警、模拟考试、上线后复盘，以及改流程前必须经理批准。

GitHub 的 review skills 和 MCP 像给代码评审员配了两样东西: 一本公司内部规范手册，以及一扇只能看的资料窗。评审员可以查 issue、文档、服务目录，但不能顺手改外部系统；评论还要说清楚“我是根据哪条规则说的”。

所以今天对你的 iPhone + Mac + Codex 工作台最有用的一句话是: 手机像对讲机，Mac 像验货台，GitHub 像留痕工单，知识库像制度手册。入口越多，越不能靠口头信任；要靠权限表、指标、评审和复盘。

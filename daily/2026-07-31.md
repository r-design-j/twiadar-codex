### Codex/GPT 工作流启发

1. `AGENTS.md` 正在从“提示说明”变成“评审规则资产”

OpenAI Developers 的 Codex Code Review rules 示例说明，规则应写团队真正反复解释、且默认模型难以凭通用知识知道的约束，例如 wire protocol 兼容、外部集成面、数据边界和安全例外。规则太泛会制造噪音；规则太贴近临时代码名又会过期。最稳的写法是: 不变量 + 违规风险 + 安全替代路径。

2. 评审 agent 需要“能引用来源”的判断

Codex review 可把命中的 repository rule 引用到 finding 里，价值不只是更聪明，而是让 review 变成可追溯流程。对 AI Radar 仓库来说，适合写入规则的是: `source-cards` 条数必须等于 `metrics.sourceCards`，`report-data.js` 必须和 JSON 同步，公开产物不得包含本机路径、cookie、私信、截图和密钥。

3. 手机不是小终端，而是工程控制面

OpenAI Remote 文章把 iPhone 的价值说清楚: 选 host、选仓库、选 worktree、queue/steer、审批命令、查看 diff/test、管理长会话状态。手机端适合做方向和卡点决策，不适合把复杂命令、长 diff 和发布终审塞进小屏。

4. Queue/Steer 应成为长任务协作的基础动作

Queue 适合“当前任务完成后再做”，Steer 适合“正在跑的任务需要立刻改变方向”。这对每日自动化很实用: 采集中发现新官方源可 Steer；验证阶段想追加扫描则 Queue；进入 commit/deploy 后不要随意 Steer，避免发布链路被半路改写。

5. 私有 MCP 的正确默认不是公网暴露，而是窄 outbound 通道

Secure MCP Tunnel 的核心不是“更方便的隧道”，而是把边界反过来: 客户端在私有环境内主动连出，OpenAI 侧排队请求，私有 MCP 地址只在客户环境内部使用。对个人工作流的类比是: 任何本地 Obsidian、私有脚本、公司内网工具接入 agent 前，都应先问是否能用本地可检查 adapter，而不是开公网地址。

6. GitHub Agentic Workflows 把自然语言自动化推向仓库内治理

GitHub 文档显示 agentic workflow 用 Markdown 描述触发、权限、网络、工具和输出，再编译为 hardened Actions workflow，并支持 Copilot、Claude、OpenAI Codex、Gemini 等 engine。它适合把“每天巡检仓库/生成状态/创建 issue”这类重复工作从口头任务变成仓库资产。

7. Claude 的 Cowork web/mobile 与 memory 更新说明同行都在做同一件事

Claude 7 月 release notes 提到 Cowork 扩展到 web/mobile、任务可远程保存和继续，memory 从每日摘要转向可分类条目。它和 Codex Remote、OpenAI memory 改进指向同一趋势: 长任务需要跨设备状态、可管理记忆和可终止边界。

8. Claude Code Review 的 trigger/cost 设计提醒我们别把 AI review 默认无限触发

Claude Code Review 支持 PR 创建后一次、每次 push、手动触发三种模式，并显示平均 review 成本。对个人仓库而言，默认可以先手动触发；当规则稳定、误报低、成本可接受时，再提高触发频率。

### iPhone + Mac + Codex 协作玩法

今日推荐链路:

1. iPhone / ChatGPT Remote: 新任务先选 host、repo、branch/worktree；短消息只用于目标、边界和卡点。
2. Queue/Steer: 新增验证项用 Queue；采集方向错误或权限风险用 Steer；commit/deploy 阶段尽量冻结方向。
3. Mac/Codex: 做真实文件编辑、JSON/JS 同步、验证命令、git commit、push、Vercel deploy。
4. `AGENTS.md` / knowledge: 把反复检查项写成规则: source-card count、公开路径扫描、Vercel Ready、无非公开来源。
5. MCP/插件: 私有工具只走明确白名单和可检查 adapter；不要为了“方便”暴露公网隧道。
6. 长会话换车: 任务跑长后先输出状态、文件、验证、失败边界，再换新任务继续。

### 可沉淀知识卡片

#### 卡片 1: Repository Rules 评审资产

- 概念: 把团队反复解释的非显然规则写入 `AGENTS.md`，让 Codex review 能按规则发现问题并引用来源。
- 适用场景: 兼容性、公开数据边界、发布验收、source-card/report 同步、设计系统约束。
- 操作步骤: 选一个高后果不变量 -> 写风险和安全替代路径 -> 放在最窄目录 -> 用违规/安全/无关三类 PR 测试 -> 按误报更新。
- 风险: 泛泛规则会制造噪音；过细实现名会很快过期。
- 原文: https://developers.openai.com/blog/custom-code-review-rules-for-codex

#### 卡片 2: 手机控制面协议

- 概念: iPhone 负责选择环境、派工、Queue/Steer、审批和状态管理；真实执行、复杂 diff、发布和权限终审留在 host/Mac。
- 适用场景: Codex Remote、长任务自动化、移动审批、外出时处理卡点。
- 操作步骤: 先选 host/repo/worktree -> 说明目标和禁止动作 -> 运行中区分 Queue/Steer -> 审批最窄权限 -> 发布前回 Mac 看证据。
- 风险: 把手机当小终端会漏看 diff、路径、权限和失败细节。
- 原文: https://developers.openai.com/blog/mastering-codex-remote-for-engineering

#### 卡片 3: 私有工具窄通道

- 概念: 私有 MCP/内部 API 不应直接暴露公网；更稳的方式是 customer-run client 在私有环境内主动连出，并只转发白名单目标。
- 适用场景: Obsidian、本地脚本、公司内网工具、私有知识库、内部 REST API。
- 操作步骤: 明确目标服务 -> 限定方法/路径/超时/响应大小 -> 本地 client 发起 outbound 连接 -> 记录健康检查和日志 -> 禁止泛化成 VPN。
- 风险: 隧道若变成任意网络桥，会把工具接入升级成安全边界事故。
- 原文: https://developers.openai.com/blog/connect-private-mcp-servers-to-openai-products

#### 卡片 4: Agentic Workflow 仓库化

- 概念: 重复自然语言自动化应进入仓库: Markdown workflow 描述触发、权限、网络、工具、safe outputs，再编译成 hardened Actions。
- 适用场景: 每日仓库巡检、日报生成、issue 摘要、PR 准备、知识卡更新。
- 操作步骤: 写 workflow.md -> 声明最小权限和网络 -> 指定 engine -> 配 safe outputs -> 编译 lock workflow -> 用手动触发先跑。
- 风险: 口头自动化难审计；仓库化后也要避免给过宽 token 和网络权限。
- 原文: https://docs.github.com/en/enterprise-cloud@latest/copilot/concepts/agents/about-github-agentic-workflows

## 白话版

今天可以理解成: AI 写代码这件事，正在从“找个聪明同事帮忙”变成“给同事配制度、门禁、工牌、巡检表和对讲机”。

`AGENTS.md` 就像公司墙上的岗位红线。不是写“请认真工作”这种空话，而是写“这个接口名字不能改，因为下游还在听”“公开网页不能出现本机路径”“日报 JSON 和 JS 必须同步”。Codex review 看到问题时，还能说“我是按墙上这条规则判断的”。

iPhone 像对讲机和调度屏，不是小号 Mac。你可以在手机上派任务、看进度、批准安全命令、告诉 Codex 先排队还是立刻转向；但真到验货、看 diff、发布网站，还是回 Mac。小屏幕适合下判断，不适合扛所有细节。

Secure MCP Tunnel 像给仓库开了一扇只出不进的小门。不是把仓库大门敞开给外面，而是仓库里派一个可检查的同声传译出去取任务，只能去超市上架清单里写好的货架。这样私有工具能被 AI 用到，但边界不会糊成一团。

GitHub Agentic Workflows 则像把每天口头交代的巡检任务写成正式值班表: 几点触发、能看什么、能写什么、谁来执行、输出放哪里，全都进仓库。这样以后换人、换模型、换入口，也不至于每次重新口述一遍。

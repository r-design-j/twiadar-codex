### Codex/GPT 工作流启发

1. 8 月 14 日的 Codex 更新值得合并看: import、Computer History、Linux 桌面、web AGENTS.md 编辑和环境路由不是五个零散功能，而是在解决“同一个人、同一个仓库、多个 agent/设备/入口之间如何保持上下文一致”。
2. 导入既有 agent 设置到 AGENTS.md 的意义不是迁移一次配置，而是把 Claude Code、Cursor、Gemini CLI 等工具里的规则转成 repo 可审查资产。对团队来说，迁移后要做去重、权限降级和过期标注。
3. Computer History 让 Codex 更像熟悉本机工作台的助手，但这类记忆必须分层: 长期偏好可保留，高漂移事实要设失效时间，涉及隐私或账号状态的内容不得进入公开日报。
4. Linux 桌面预览说明 Codex 桌面工作台不再只围绕 macOS。跨平台后，路径、shell、可用 GUI、Keychain/凭证、sandbox 和本地 app 能力必须显式记录。
5. Web 端改 AGENTS.md 和路由任务到不同环境，会降低启动成本，也更容易造成“规则在哪里生效、任务跑在哪台机器、哪边完成”的混淆。任务记录里要固定 rule source、target env 和 final evidence owner。
6. Codex 0.147.0 及近期 release 节奏说明 agent 工作台层仍在快速变化。自动化报告不应把某个 CLI 行为当长期事实；每期应记录版本或用文档链接代替口头假设。
7. OpenAI background mode 适合长研究和报告生成，但 async accepted 不是完成。它必须和 polling、artifact readback、timeout、handoff、人工停止条件绑定。
8. Agents SDK 的 handoff、guardrails、tracing、MCP 工具让多 agent 应用更像软件系统。个人自动化可以先借用这个结构: planner、collector、writer、reviewer 分开，但写入和发布只保留一个 owner。
9. GitHub Copilot code review 与 custom instructions/MCP 能把“审查偏好”变成仓库级资产。AI Radar 可以把公开边界、JSON contract、source quality、secret scan 变成 review rule pack。
10. GitHub MCP registry 和 stateless MCP 的方向是把工具连接从“我装了一个服务”变成“可发现、可配置、可无状态连接的工具目录”。自建 MCP 不应急着暴露公网，先做最小工具面和权限清单。
11. Claude Code hooks 与 subagents 仍是有用参照: hook 负责确定性闸门，subagent 负责职责隔离。Codex 侧也应保持只读扫描、写入执行、最终验收分层。
12. Obsidian Web Clipper 适合继续做公开资料沉淀，但今天更应该增加“迁移/回放/权限/审查”字段，而不是只剪标题和摘要。

### iPhone + Mac + Codex 协作玩法

今日推荐链路:

1. iPhone/Remote: 发起任务时只写目标、公开边界、是否允许发布和低风险转向。
2. Chat: 把输入整理成任务胶囊，冻结当天主题、Top 5、排除项和验收标准。
3. Luna/只读侧车: 扫描公开候选源，只回传 JSONL，不写文件、不发布。
4. Mac/Codex: 写 daily、source-cards、knowledge、site data，并保留本地验证证据。
5. Computer History: 只用于提升本地上下文理解，公开日报不暴露本地历史细节。
6. AGENTS.md: 把跨工具迁移后的规则做成 repo 资产，避免规则散落在各个 agent app。
7. GitHub/Review Rule Pack: 发布前自动检查数据合同、公开边界、链接、diff 和部署证据。
8. Vercel/GitHub: 只用 commit、push、deployment Ready 作为公开发布完成证据。

### 可沉淀知识卡片

#### 卡片 1: Agent Context Migration Sheet

- 概念: 从 Claude Code、Cursor、Gemini CLI 或旧 Codex 设置迁移到 AGENTS.md 时，要把上下文、权限和生效范围做成表，而不是直接合并所有规则。
- 操作步骤:
  1. 列出来源工具、原始规则文件、仓库路径和最后更新时间。
  2. 给每条规则标注类型: 风格、命令、权限、安全、测试、发布、记忆。
  3. 删除重复、冲突、过期和仅适用于旧工具的规则。
  4. 对高风险规则写 owner、适用路径、禁止动作和升级条件。
  5. 迁移后运行一次小任务验证规则是否真实生效。
  6. 把接受/拒绝的规则和原因写入本地回执。
- 风险: 迁移不是复制粘贴；把旧工具的宽权限带进新 agent，会扩大误操作面。

#### 卡片 2: Computer History Replay Ledger

- 概念: 本机历史上下文能提高 agent 连续性，但必须记录哪些上下文可用于推理、哪些不能进入公开输出。
- 操作步骤:
  1. 标注本次是否使用本机历史、自动化记忆或项目记忆。
  2. 区分长期偏好、项目约定、当天事实和高漂移事实。
  3. 给高漂移事实写采集日期和失效条件。
  4. 公开输出前扫描本地路径、账号状态、截图、通知和私密内容。
  5. 结尾写入本次接受的记忆更新和未接受项。
  6. 下次运行先读最近记忆，避免重复主题。
- 风险: 记忆能省时间，也会把旧事实伪装成当前事实；公开日报只能写脱敏结论。

#### 卡片 3: Permission Gate Matrix

- 概念: 多入口 agent 工作流必须把读、写、发布、外发和审批动作分开，不让同一个入口自动拥有全部权限。
- 操作步骤:
  1. 按 Chat、Tasks、Work、Codex、Remote、Slack、GitHub、API 列入口。
  2. 为每个入口标注 read、write、publish、external action、approval 五列。
  3. 写清凭证来源、服务账号、连接器、MCP 工具和撤销路径。
  4. 高影响写动作默认 always ask 或 safe output。
  5. 最终证据只允许来自 Mac/Codex、本地测试、GitHub、Vercel 或平台 Ready。
  6. 每次新增 connector 前先更新矩阵。
- 风险: 入口越顺手，越容易把“能看到任务”误认为“有权完成任务”。

#### 卡片 4: Review Rule Pack

- 概念: 高频自动化应该把发布前审查做成可复用规则包，减少每次靠人工临场记忆。
- 操作步骤:
  1. 固定数据合同: sourceCards、signals、knowledge、report-data 同步。
  2. 固定公开边界: cookie、截图、私信、凭证、本地路径不进入公开文件。
  3. 固定来源质量: Top 5 必须能回到公开原文，优先官方/一手。
  4. 固定工程检查: node --check、JSON parse、JSONL required fields、git diff --check。
  5. 固定发布证据: commit、push、deploy URL、inspect Ready。
  6. 失败时生成部分完成报告，不破坏性重试。
- 风险: AI 审查只能提高覆盖率，不能替代真实测试、真实 deploy 和人工最终判断。

## 白话版

今天这期像是家里从“请一个临时工”升级成“固定装修队 + 工具间 + 施工日志 + 门禁卡”。

以前 agent 能干活就不错了。现在问题变成: 它从哪套老规矩接手？它记得你家哪些历史？它在哪台机器上干？它能不能动电闸、能不能开门、能不能自己下单？完工以后谁验收？

AGENTS.md 导入像把不同师傅手里的施工规矩统一贴到墙上；Computer History 像老师傅记得你家水管怎么走，但不能把你家隐私写到门口公告栏；Linux 桌面预览像施工队不只在一套房干活，还要能去不同户型；permission matrix 像门禁卡，谁能看、谁能改、谁能付款都要分开；review rule pack 像验收清单，每次交付都按同一张表检查。

所以今天的结论很简单: 不要只收藏好 prompt，要收藏能迁移、能回放、能限权、能验收的工作台资产。

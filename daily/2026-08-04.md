### 今日结论

2026-08-04 的主线是: AI 工作台正在从“多个入口分别提效”升级为“一个可治理的跨设备执行系统”。OpenAI 7 月的 ChatGPT Work、桌面端 Chat/Work/Codex 合并、Sites 公测、Plugin Directory、Codex Remote GA 与 Record & Replay，说明产品层已经把聊天、长任务、代码、网页产物、插件能力和移动审批放进同一条链路；Apple WWDC26 的 MLX 本地 agent 与多 Mac 分布式推理，则把另一端补齐: 敏感代码和高频验证可以留在本机/本地集群执行。

### Codex/GPT 工作流启发

1. 入口合并后，任务边界更重要

ChatGPT Work、桌面端 Chat/Work/Codex、Sites 和 Plugin Directory 的共同点不是“按钮更多”，而是把不同工作形态放进一个应用里。个人工作台应明确: Chat 处理问答和判断，Work 处理多步骤交付，Codex 处理代码和本地环境，Sites/Vercel 处理公开展示，插件处理特定能力包。入口越统一，越要把每类入口的读写权限、产物和验收条件写清。

2. iPhone 是派单台，不是终审台

Codex Remote GA 后，手机可以连接 Mac/Windows host，查看进度和批准动作。正确用法是把手机当作派单、审批、转向和状态面板；涉及 diff 终审、密钥、发布、公开路径扫描和部署证据时，仍应回到 Mac/Codex。

3. 本地 agent lane 开始有工程意义

Apple 的 MLX agent 演示给出一个重要方向: 并非所有 agent 工作都应该默认上云。本地模型可以通过 OpenAI-compatible endpoint 接到现有 agent，读取代码、调用命令、跑 Xcode build，并在 Apple silicon 上利用连续批处理和多 Mac 分布式推理。适合放在本地 lane 的任务包括私有代码探索、构建错误复现、低风险重构草稿和离线验证。

4. Codex CLI 是跨工具互通的锚点

Codex CLI 不只是命令行入口，也承载登录、配置、approval mode、resume、插件互通和本地执行习惯。codex-plugin-cc 的价值正是复用本机 Codex CLI 和 app server，让 Claude Code 用户可以调用 Codex 做 review/rescue，而不用重新搭一套 runtime。

5. 双 agent 不等于自动合并

codex-plugin-cc、cc-plugin-codex、Degen Sing 的 orchestration 案例都指向同一件事: 多 agent 最有价值的是分工与制衡，不是让它们无限循环。比较稳的默认是“一个负责规划/实现，一个负责只读审查或对抗审查，最后人类做合并/发布判断”。

6. 企业采用信号开始转向可度量

Business Insider 关于 Disney 切换 AI coding 工具组合的报道说明，大公司正在从“试用 coding assistant”转向“按开发速度、使用率、成本、满意度和 dashboard 管理工具组合”。个人自动化也应记录 sourceCards、signals、knowledge、commit、deploy、失败原因和人工拍板项，否则无法判断是否真的提效。

7. Sites/公开网页要进入发布验收链

ChatGPT Sites 和本仓库 Vercel 站点本质类似: agent 可以产出公开页面，但公开交付必须有数据契约、隐私边界和发布状态证据。日报站点的最低验收仍是 JSON 可解析、JS fallback 同步、signals/knowledge 数量正确、公开路径无敏感信息、Vercel inspect Ready。

8. 旧浏览器/新浏览器迁移提醒边界治理

Release Notes 提到 Atlas 将在 2026-08-09 停止工作，并把 browser-based agentic capability 转向 ChatGPT/Codex 桌面体验。对个人工作流的启发是: 浏览器、书签、cookie、历史记录属于高敏感入口；日报只记录公开链接和总结，不记录浏览器私有状态。

### iPhone + Mac + Codex 协作玩法

今日推荐链路:

1. iPhone: 用 ChatGPT mobile 记录公开链接和一句目标，启动或 Queue Codex task。
2. Work/Chat: 需要研究、整理和文档时走 Work；只做判断/解释时走 Chat。
3. Mac/Codex: 对代码、文件、JSON、发布、测试和 Git 操作保持本地执行与本地验收。
4. Local MLX lane: 对私有代码或离线验证，先尝试本地 agent 读写/构建/复现，输出证据后再决定是否上云。
5. Plugin Directory: 每个插件先过“超市上架清单”: 需要什么 app、读什么、写什么、谁能装、如何撤销。
6. Dual review: 重要 PR 用 Codex 只读审或对抗审，不让第二个 agent 直接合并。
7. Sites/Vercel: 公开页面只展示公开来源、作者、链接、总结和知识卡，不展示私有路径或登录态。

### 可沉淀知识卡片

#### 卡片 1: 四入口分工表

- 概念: 把 Chat、Work、Codex、Sites 分别定义为判断、长任务、代码执行、公开交付四类入口。
- 适用场景: 每日晨报、研究报告、代码修复、公开网页发布。
- 操作步骤: 先判定入口 -> 写成功标准 -> 标注读写权限 -> 固定产物路径 -> 用测试/发布证据收口。
- 风险: 入口统一后容易把所有任务塞进同一会话，造成上下文污染和验收不清。
- 原文: https://help.openai.com/en/articles/6825453-chatgpt-release-notes

#### 卡片 2: 本地 agent lane

- 概念: 对私有代码、离线验证和高频构建，先让本地模型/本地 agent 读写、构建、复现，再决定是否交给云端。
- 适用场景: Xcode 项目、私有仓库、GUI-only bug、低风险重构草稿、多 Mac 本地推理。
- 操作步骤: 启动本地模型服务 -> 接入 agent/OpenAI-compatible endpoint -> 限定工具 -> 跑 build/test -> 输出 diff 和日志摘要。
- 风险: 本地模型能力、上下文长度和工具权限不稳定，不能免除人工验收。
- 原文: https://developer.apple.com/videos/play/wwdc2026/232/

#### 卡片 3: 双 agent 审查门

- 概念: 一个 agent 做规划/实现，另一个 agent 做只读审查或对抗审查，最终由人类合并和发布。
- 适用场景: PR review、迁移、认证/计费/安全变更、长任务换车。
- 操作步骤: 先定义主 agent 产物 -> 第二 agent 只读审查 -> 汇总阻塞项 -> 主 agent 修复 -> 人工看 diff/test/deploy。
- 风险: 两个 agent 互相改会产生预算黑洞和责任不清。
- 原文: https://github.com/openai/codex-plugin-cc

#### 卡片 4: 插件上架清单

- 概念: 插件是 skills、apps、app templates 的能力包；安装前要像超市上架一样审核能力、权限、角色和撤销方式。
- 适用场景: Plugin Directory、Sites、GitHub、Vercel、Gmail、Figma、私有 MCP。
- 操作步骤: 看插件包含什么 -> 是否需要 app 连接 -> 标注读/写动作 -> 配角色 -> 低风险测试 -> 记录撤销路径。
- 风险: 把插件当普通提示词会低估外部动作和数据权限。
- 原文: https://help.openai.com/en/articles/20001256-plugins-in-codex/

## 白话版

今天这期可以理解成: 以前你有很多零散工具，像不同门店各管一摊；现在它们正在变成一个带前台、车间、质检和展厅的工厂。

Chat 是前台，适合问路、判断、快速讨论。Work 像项目经理，适合把一件长活从资料、分析、文档一路推进。Codex 是车间，真正碰代码、跑测试、改文件。Sites/Vercel 是展厅，最后给别人看的东西必须干净、可访问、可解释。

iPhone 像派单台。你可以在外面说“先查这个链接”“这个方向不对，停一下”“这个命令可以批准”。但验货、签字、发货，还是要回 Mac。手机看得快，但不适合做最后质检。

Apple 的 MLX 本地 agent 像你家里多了一台小型加工机。不是所有材料都要送到云端大工厂，有些私密图纸、简单试切、构建验证，可以先在自己机器上跑一遍。跑通了再决定要不要交给云端。

codex-plugin-cc 像请第二个师傅验货。第一个师傅负责做，第二个师傅负责挑毛病。好处是能发现盲区；坏处是如果让两个师傅互相改、互相吵，工期和预算会烧掉。所以最后合不合、发不发，还是你拍板。

插件目录就是超市货架。每个插件上架前要看清楚: 它能拿什么数据，能不能写东西，谁能用，怎么撤下来。不能因为包装写着“提效”就直接放进生产线。

### Codex/GPT 工作流启发

1. 多入口不是多套规则

GitHub managed settings 把 Copilot app 和 cloud agent 拉进同一套企业策略。对应到个人 Codex 工作台，手机、桌面、CLI、Work、Remote、GitHub Mobile 可以都是入口，但权限、插件白名单、审批绕过、URL 访问和发布边界必须只有一套主口径。

2. 客户端权限要单独列

Copilot app 有独立 policy，说明“能用 CLI”不等于“能用 app”，“能跑 cloud agent”也不等于“能让手机触发修复”。AI Radar 可以新增一个入口权限矩阵: iPhone 只读采集和派工；Codex 本地写文件；Mac 终审发布；Vercel/GitHub 需要显式验证。

3. Work 和 Codex 的边界要写清

官方 Help Center 明确: Work 面向研究、分析、文档、表格、报告和 Sites；Codex 仍面向本地仓库、终端和开发工具；Voice 使用所选体验的工具和权限。实际使用时，不要把 Work 的云同步和 Codex 的本地历史混为一谈。

4. 手机可以修 CI，但只能交草案

GitHub Mobile 的新流程是从失败 check 触发 Copilot cloud agent，它会在原 PR 之上开新 PR，并让用户 review。这个设计值得照搬: 手机端可以触发修复和续跑，但最终 merge、deploy、费用和公开边界仍回 Mac。

5. Issues automation 的理由和置信度是通用格式

GitHub Issues automation controls 把 rationale、confidence、approvals 做成元数据动作的标准结构。AI Radar 的 source-card、signals 分类、候选关注账号也应沿用: 每条卡片有 why_it_matters、actionable_takeaway、confidence，低置信度进入待确认。

6. MCP stateless 是 7 月 28 日的工具链分水岭

GitHub MCP Server 支持 2026-07-28 生效的 stateless spec，并强调 conformance tests。个人私有 MCP 或本地桥验收不能只看“能连上”，还要看无 session 假设、认证边界、日志/secret scanning、elicitation 和协议一致性。

7. 提示方式从“指挥步骤”转向“定义结果和边界”

Claude Code 创建者关于少微管理的建议，和 Anthropic 对 40 万 Claude Code session 的研究相互印证: 人负责目标、约束和验收，agent 负责执行细节。好 prompt 不是列 30 步，而是讲清目标、不可碰边界、证据和停止条件。

8. 跨岗位任务需要权限同步

OpenAI 的工作研究显示，许多职业正在借用其他岗位任务。AI Radar 这种个人自动化也一样: 它既像研究员，也像编辑、数据整理员和发布工程师。每多一个“岗位动作”，就要同步更新可读/可写/可发布边界。

### iPhone + Mac + Codex 协作玩法

今日推荐链路:

1. iPhone / GitHub Mobile 只做入口: 收集公开链接、触发 CI 调查、补上下文、看等待状态。
2. Work 用于公开资料研究、日报草稿、知识卡片和报告结构，不接触本地私密文件。
3. Codex 本地执行仓库文件更新、JSON/JS 同步、校验脚本和 Git 操作。
4. GitHub / Linear / Issues automation 只接收带 rationale、confidence、review step 的候选动作。
5. Mac 端统一检查入口权限矩阵、diff、source-card 数量、secret/path 扫描、commit、push、Vercel Ready。
6. 每次新增入口前先问: 这个入口能否绕过原有审批？日志在哪里？失败后谁终审？

### 可沉淀知识卡片

#### 卡片 1: 多入口控制表

- 概念: 当同一个 agent 工作台出现 web、mobile、desktop、CLI、cloud/local 多入口时，需要一张统一的入口权限表。
- 适用场景: ChatGPT Work、Codex Remote、GitHub Mobile、Copilot app、cloud agent、自动化发布。
- 操作步骤: 列入口 -> 标注执行环境 -> 标注可读/可写/可批准 -> 标注日志位置 -> 标注终审人和停止条件。
- 风险: 不同入口默认继承权限，会形成“手机能绕过桌面审批”的隐性通道。
- 原文: https://github.blog/changelog/2026-07-27-enterprise-managed-settings-now-apply-to-the-github-copilot-app/

#### 卡片 2: 入口隔离策略

- 概念: 客户端 policy 应单独管理，避免把 CLI、desktop、mobile、cloud agent 混成一个权限开关。
- 适用场景: Copilot app、Codex CLI、GitHub Mobile、Work、Remote、内部工具。
- 操作步骤: 为每个入口设开关 -> 分别配置插件和网络访问 -> 检查是否允许绕过审批 -> 记录可回滚策略。
- 风险: “同一账号已授权”不等于“所有入口都适合执行同一类动作”。
- 原文: https://github.blog/changelog/2026-07-27-manage-github-copilot-app-access-with-a-dedicated-policy/

#### 卡片 3: 移动端修复草案

- 概念: 手机端可以触发 agent 调查和修复失败 CI，但产物应是草案 PR 或候选 diff，而不是直接合并。
- 适用场景: GitHub Mobile、Codex Remote、iPhone 上的故障响应、通勤途中处理阻塞。
- 操作步骤: 从失败信号触发 -> agent 开草案 -> 等待 review -> Mac 跑附加检查 -> 人工决定 merge/deploy。
- 风险: 手机屏幕不足以完成复杂 diff、权限、费用和公开发布终审。
- 原文: https://github.blog/changelog/2026-07-23-github-mobile-fix-failing-actions-checks-with-copilot-cloud-agent/

#### 卡片 4: 结果边界提示法

- 概念: 对成熟 coding agent，应少给逐步指挥，多给目标、边界、证据、验收标准和停止条件。
- 适用场景: Codex、Claude Code、multi-agent、长任务自动化、报告生成。
- 操作步骤: 写目标 -> 写不做什么 -> 写必须保留的上下文 -> 写验证证据 -> 让 agent 自选步骤 -> 审查轨迹。
- 风险: 只说“随便优化”会目标漂移；逐步 micromanage 又会浪费 agent 的执行能力。
- 原文: https://www.anthropic.com/research/claude-code-expertise

## 白话版

今天的 AI 工具像一家店开了很多门: 正门、侧门、手机小程序、员工后台、外卖入口都能接单。问题不是门多不好，而是收银、仓库、退款、上架这些规矩必须是一套。

OpenAI 的工作研究说，AI 正在让人跨岗位干活。以前设计师要找工程师，销售要找分析师，现在很多事情可以先自己让 AI 搭一版。但这也意味着，一个“研究助理”可能突然开始像编辑、数据员、发布工程师一样做事。岗位变多，权限表也要跟着变。

GitHub 的两条更新很像给店门装门禁: Copilot app 有独立开关，cloud agent 和 app 也要吃同一套 managed settings。翻成 Codex 工作台，就是 iPhone、Mac、CLI、Work、Remote 不能各玩各的。入口可以多，规矩只能有一份。

GitHub Mobile 修 CI 的设计也很克制: 手机上一点，让 agent 去查失败 check、开一个新 PR，然后叫你 review。它没有说“手机直接合并”。这正适合我们的 iPhone + Mac + Codex: 手机像遥控器，负责叫人来修；Mac 像验货台，负责看清楚再上架。

Claude Code 那边的信号则是: 别像盯实习生一样每一步都念给 agent 听。你要像给靠谱外包下单: 我要什么结果、不能碰什么、怎么验收、失败就停在哪里。路线让它自己走，但交付必须拿证据说话。

所以今天最该补的不是新工具，而是一张“门禁表”: 这个入口能看什么、能改什么、能不能批准、出了事谁兜底。

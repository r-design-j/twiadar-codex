### Codex/GPT 工作流启发

1. GPT-5.6 的核心变化不是“所有任务都用更强模型”，而是任务启动时必须显式选择模型、推理档位和验收深度。
2. API latest-model 文档适合做升级闸门: 先评估合同、成本和回滚，再替换生产调用。
3. Developers 首页把 Chat、Work、Codex、Plugins、MCP 放在同一入口，说明“聊天、做文档、改代码、连工具”会越来越像同一工作台里的不同工位。
4. Codex use cases 的关键词是 reusable: teammate、feedback、skills、verified operations、Slack/iMessage、docs、security、macOS、Sites。日报不应只收藏新闻，而要把用例转成 capsule。
5. Community showcase 的高价值信号不是炫技，而是任务形状: 过夜任务、硬件 dashboard、EPUB reader、Three.js 动画、Codex app server、handoff experience，都能反推可复用流程。
6. GitHub agent app metrics 证明多 agent 时代不能只问“哪个好用”，要记录 agent_id、入口、job starts、sessions、接受率和返工率。
7. per-model token breakdown 把模型路由变成运营指标。个人也应记录 Sol/Luna/fast mode 或外部模型的实际使用面，避免凭感觉选模型。
8. Agent Plugins 1.0 和 agent finder 合起来说明工具不是越多越好，而是要可发现、可上架、可拒绝、可审计。
9. Copilot weekly release 里的 `/btw` side chat 说明 agent 工作中途的“旁路提问”会成为常态。旁路问题不能改主线目标，除非显式转成 steering message。
10. Markdown hybrid diff 对 AI 写作和文档工作很有价值: 文档 diff 应该像代码 diff 一样可审阅、可回滚、可定位。
11. on-device multilingual dictation 提醒语音输入适合 capture intent，但仍要发送前编辑和验收后证据，不把语音当最终指令源。
12. ChatGPT Record / workspace agents / Work 类型资料的共同点是: AI 正在从“回答问题”转为“把会议、资料、上下文加工成可交付物”。
13. private MCP 边界是关键安全线: 私有 MCP 可以被访问，不代表应该公开暴露；隧道、鉴权和审计记录要分开。
14. Obsidian Web Clipper 仍是知识回灌入口，但模板要保存公开标题、来源、takeaway 和复用标签，不保存登录态或私有上下文。

### iPhone + Mac + Codex 协作玩法

今日推荐链路:

1. iPhone/Remote: 发起任务时只写目标、允许动作、停止条件、预算档位和是否允许发布。
2. Chat: 把口语化目标压成任务 capsule，并选择模型路由: Sol 主验收、Luna 只读侧车、外部通道仅在边界允许时使用。
3. Capability Catalog: 启动前查可用 skill、plugin、MCP、browser、GitHub 或 Sites，不把所有工具一次性塞进上下文。
4. Side-Question Log: 主任务运行中有疑问时先旁路记录，不直接改主线；确需改方向时生成 steering message。
5. Mac/Codex: 执行文件写入、检查、diff、commit、push、deploy；同一写入对象只保留一个 owner。
6. Usage Ledger: 结束时记录入口、模型、推理档位、耗时、sourceCards、signals、knowledgeCards、验证、是否一次通过。
7. Knowledge 回灌: 把今天的模型路由、能力目录、旁路提问和使用账本沉淀到当月 knowledge。
8. Review: 每周回看哪些任务适合低档/快档，哪些需要 Sol 深审或人工复核。

### 可沉淀知识卡片

#### 卡片 1: Model Routing Card

- 概念: 每类任务启动前先写模型路由，不默认使用最高档，也不为了省钱牺牲必要验收。
- 操作步骤:
  1. 标注任务类型: 写作、代码、研究、视觉、发布、审查或日常自动化。
  2. 选择主模型、侧车模型、推理档位和预算上限。
  3. 写清不适用条件: 高风险、安全、隐私、外部副作用、缺证据。
  4. 记录验收深度: 轻审、深审、真实发布或人工复核。
  5. 结束时补充耗时、是否一次通过、返工原因和下次默认档位。
- 风险: 没有路由卡，团队会在“贵但稳”和“便宜但返工”之间靠感觉摇摆。

#### 卡片 2: Capability Catalog

- 概念: 把 skills、plugins、MCP、browser、GitHub、Sites、local scripts 做成能力目录，按任务需要加载，不把全部能力塞进上下文。
- 操作步骤:
  1. 为每个能力记录名称、用途、入口、读写边界和 owner。
  2. 标注状态: 可用、需安装、需授权、只读、禁用。
  3. 写清可处理任务和不能处理任务。
  4. 高风险写动作必须有审批和撤销路径。
  5. 每次任务只加载最小必要能力，结束后记录是否有效。
- 风险: 工具太多会放大权限面；没有目录会让 agent 临时乱找工具。

#### 卡片 3: Side-Question Log

- 概念: 长任务中途的问题要先作为旁路问题记录，避免打断主 agent 的执行上下文；只有确认会改变目标时才升级为 steering message。
- 操作步骤:
  1. 记录问题、触发上下文、是否影响目标和期望回答。
  2. 不让旁路问题直接修改文件、发布或改变权限。
  3. 回答后标注: 仅供理解、补充检查、改变计划、暂停执行。
  4. 若改变计划，生成新的任务 capsule 并重新冻结边界。
  5. 结束时把有价值的问题回灌到 FAQ 或 playbook。
- 风险: 旁路聊天很方便，但容易把“顺手问一句”变成隐式改需求。

#### 卡片 4: Agent Usage Ledger

- 概念: 多 agent 时代要记录真实使用，而不是凭印象评价哪个 agent 好。
- 操作步骤:
  1. 记录入口、agent/model、reasoning、工具、任务类型和开始时间。
  2. 记录产物、验证命令、通过/失败和是否发布。
  3. 记录耗时、tokens/credits/cost 可得值和人工返工点。
  4. 用稳定 ID 归并同一 agent，不只看 display name。
  5. 每周按接受率、返工率、成本和任务类型更新默认路由。
- 风险: 没有账本，多 agent 路由会变成品牌偏好；有账本才能持续降本提质。

## 白话版

今天这期像是给 AI 工作台加了“值班表、工具库、便签纸和水电表”。

值班表就是 Model Routing Card: 什么事该让 Sol 深想，什么事可以让 Luna 快跑，什么事只能 Mac/Codex 最后验收。不是每次都派最贵的人，也不是为了省钱让不合适的人硬干。

工具库就是 Capability Catalog: skills、plugins、MCP、GitHub、Sites、浏览器都像超市货架。要先知道哪些商品上架、能干什么、有没有写权限、谁负责撤掉；不能每次开工都把整家超市搬进工地。

便签纸就是 Side-Question Log: 施工中途你想问一句“这个墙为什么这么画”，可以先贴便签，不要直接让施工队改方案。真要改方向，就写成正式变更单。

水电表就是 Agent Usage Ledger: 不能只说“这个 agent 感觉好用”。要记谁干了什么、用了多久、花了多少、结果有没有被接受、返工在哪里。记久了才知道哪些活该用深审，哪些活快档就够。

所以今天的结论很简单: AI agent 越多，真正值钱的不是多开几个窗口，而是把模型选择、工具选择、旁路问题和用量复盘做成稳定制度。

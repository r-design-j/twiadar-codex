## 官方严谨版

### 今日结论

2026-08-15 的主线是: AI 工作台正在从“单次对话或单个 coding agent”升级为“跨设备、跨资料库、跨插件、跨本地/云端 agent 的受控工作面”。ChatGPT release notes 把 Linux desktop、Projects memory controls、Drive Library、Computer History、Study Mode 和 connectors 放到同一条产品主线；Codex/Responses/Agents 文档则把 CLI、本地仓库、AGENTS.md、Workspace Agent API、multi-agent、background mode、computer use、plugins、MCP、code review rules 和私有 MCP 安全连接拼成一套可配置执行面。

这意味着个人工作流的重点不再是“从 iPhone 还是 Mac 启动 Codex”，而是把每个入口的职责写清楚: iPhone/Remote 只派工、查看状态、纠偏和审批低风险转向；Mac/Codex 负责本地文件、测试、diff、commit、push、deploy；Projects、Drive Library 和 Obsidian 是资料与上下文层；Computer History 和 desktop app 是桌面状态层；Workspace Agent API、Responses background mode 和 multi-agent 是长任务/并行任务层；plugins/MCP 是工具与权限层。任何一层都不能替代最终证据链。

对 AI Radar 的直接动作是: 后续自动化应该新增一张“工作台资产清单”，把入口、资料源、记忆开关、agent API、subagent、plugin、MCP、review rule 和发布证据放在同一张表里。每次运行只读采集仍然成立，但只要引入新的连接器、插件、桌面状态、云端 agent、外部 sidecar 或私有 MCP，就必须先回答它能读什么、能写什么、记忆是否启用、是否需要确认、失败如何停止、最终证据由哪台设备收口。

### Codex/GPT 工作流启发

1. ChatGPT desktop 正在变成“桌面状态入口”

Linux app、公测桌面能力、Computer History 和 connector updates 放在一起，说明 ChatGPT 不只是网页聊天，也在靠近本地机器上下文。个人工作流要把 desktop app 当作状态入口，而不是最终发布证据入口。

2. Project memory on/off 是项目级闸门

Projects 支持更明确的 memory 控制后，长期项目可以保留偏好和背景，但日报、财务、发布这类高漂移任务仍要每次复核当天事实。memory 命中只能降低重复解释，不能替代最新采集。

3. Drive Library 和 Obsidian 是资料层，不是结论层

Drive Library、Obsidian second brain 和本地 vault 适合沉淀资料和复用素材，但资料进入日报前仍要看公开性、日期、来源和可操作性。公开网站只能写公开来源和总结后的知识卡片，不能泄露私有文档或本地路径。

4. Workspace Agent API 需要标准 job envelope

API 触发 agent run 的好处是可自动化，风险是“启动了”容易被误认为“完成了”。每个 run 都要带 repo、branch、权限、停止条件、预期产物、验收命令和回传格式。

5. Responses API 是 agent loop 的统一入口

Responses API 把多轮状态、工具调用、MCP、computer use、file/web search 放到同一个抽象里。迁移时要从“messages 列表”切到“items + state + tools + retention”的思维。

6. Background mode 适合长任务，但必须持久化 response id

后台任务能承接报告生成、批量分析和长推理，但必须轮询到终态，并记录 response id、ZDR/临时状态限制和失败停止条件。

7. Subagents 适合候选扫描和局部实现，不适合最终验收

Codex/Responses 多代理可以并行处理候选链接、局部修复或独立检查，但目标解释、权限、安全、架构、发布和验收仍由主代理收口。今天的公开候选扫描也遵循这个边界。

8. Code review rules 是仓库级“自动审稿要求”

Custom code review rules 能把团队规范写成可重复的审查规则。对日报仓库来说，类似规则可以覆盖 source card 字段、signals 计数、公开边界和 report-data 同步。

9. Computer use 的默认风险是环境暴露和页面注入

官方 guidance 的重点不是“会不会点”，而是隔离环境、清空敏感状态、人工确认高影响动作、把网页内容当作不可信输入。日报只读采集继续优先公开网页和官方文档。

10. 私有 MCP 不应靠公网隧道硬开门

OpenAI 的私有 MCP 文章强调可审计客户端、出站连接和明确目标配置。个人本地桥或 MCP 不能随手用公网隧道暴露，除非完成安全评估和显式确认。

11. iPhone 的价值是控制面，不是施工现场

iPhone/Remote 适合派工、看状态、补链接和批准低风险转向；Mac/Codex 仍是本地文件、命令、GitHub 和 Vercel 证据的收口点。这个边界今天继续保持。

12. 低延迟模型是变量，不是完成标准

GPT-5.6 Ultrafast 说明速度正在成为 agent 工作流变量，但目前仍应按预览能力处理。真正的完成标准仍是可核验产物，而不是响应更快。

### iPhone + Mac + Codex 协作玩法

今日推荐链路:

1. iPhone/Remote: 发起日报、补充公开链接、查看运行状态、批准低风险转向。
2. Chat: 判断当天主线，冻结公开边界和可写路径。
3. Drive Library/Projects/Obsidian: 存放长期可复用资料，memory 只保留稳定偏好和项目事实。
4. Workspace Agent API/Responses background: 只用于带 job envelope 的长任务，不把 run started 当完成。
5. Subagents: 只读扫描候选来源或处理独立局部任务，结果交回主代理。
6. Mac/Codex: 写五文件包、跑本地检查、审 diff、commit、push、deploy。
7. Plugin/MCP 清单: 记录每个能力的读写动作、凭证、确认、禁用和事故复核。
8. Computer use 闸: 隔离环境、高影响动作人审、页面内容按不可信输入处理。
9. Code review rules: 把日报合同写成可重复规则: 日期、JSONL 字段、signals、knowledge、公开边界。
10. Evidence gate: 只有本地文件、校验、GitHub 和 Vercel Ready 齐全才标完成。

### 可沉淀知识卡片

#### 卡片 1: 工作台资产清单

- 概念: 把入口、资料库、记忆、agent API、subagent、plugin、MCP、review rule 和发布证据放到同一张表里。
- 适用场景: 日报自动化、长研究、代码修复、跨设备派工、插件试点。
- 操作步骤: 列入口 -> 列能读什么 -> 列能写什么 -> 标记记忆状态 -> 标记确认动作 -> 绑定验收证据 -> 定期复核。
- 风险: 把产品入口、资料层、工具层和最终证据混在一起，会导致“已派工”被误报为“已完成”。
- 原文: https://help.openai.com/en/articles/6825453-chatgpt-release-notes

#### 卡片 2: Workspace Agent Job Envelope

- 概念: 每个由 API 或远程入口触发的 agent run 都要带完整工作单，而不是只带一句任务描述。
- 适用场景: Workspace Agent API、Responses background mode、Codex cloud tasks、GitHub agentic workflows、远程派工。
- 操作步骤: 写目标 -> 写 repo/branch -> 写读写边界 -> 写停止条件 -> 写交付物 -> 写验证命令 -> 写回传格式。
- 风险: API run started 不是完成证据；必须等本地或平台返回可核验产物。
- 原文: https://developers.openai.com/codex/workspace-agent-api

#### 卡片 3: 项目记忆开关闸

- 概念: 项目级 memory 必须标注启用状态、适用范围、过期规则和复核要求。
- 适用场景: ChatGPT Projects、Codex repo memory、AGENTS.md、自动化日报、个人知识库。
- 操作步骤: 判断是否需要记忆 -> 标注长期/临时 -> 高漂移事实每次复核 -> 冲突时以当前证据为准 -> 定期清理。
- 风险: 旧记忆会降低重复解释成本，也会放大过期事实。
- 原文: https://help.openai.com/en/articles/6825453-chatgpt-release-notes

#### 卡片 4: Review Rule 合同化

- 概念: 把人工反复检查的发布合同写成仓库级 review/check 规则。
- 适用场景: AI Radar daily、source cards、公开边界扫描、PR review、内容发布。
- 操作步骤: 抽取固定合同 -> 写成规则 -> 本地脚本验证 -> CI 或 review agent 复核 -> 每次失败更新规则。
- 风险: Review rule 只能辅助发现问题，不能替代最终 diff、push 和 deploy 验收。
- 原文: https://learn.chatgpt.com/blog/custom-code-review-rules-for-codex

## 白话版

今天这期像是在给 AI 工作台画一张“施工现场平面图”。

以前我们只问: 这个 AI 聊天窗口能不能帮我写东西？现在要问得更细: 哪个门进来？资料放在哪个柜子？它记不记以前的事？它能不能碰电脑状态？能不能调用外部工具？能不能开一个云端工单？最后谁来验收？

ChatGPT 的 release notes 像是在把办公室扩建: Linux 桌面入口来了，Projects 里的记忆可以开关，Drive Library 像资料柜，Computer History 像电脑操作流水账。Codex CLI 像本地施工队，Workspace Agent API 和 Responses background mode 像远程施工单，subagents 像临时小组，plugins 和 MCP 像外包工具箱，code review rules 像验收表。

但关键不是工具越多越好，而是每个工具都要贴标签。iPhone 像对讲机，负责派工和问进度；Mac/Codex 像施工现场和质检台，负责真正改文件、跑测试、提交、部署。资料柜不能当结论，开了工单不能当完工，临时小组回话不能当最终验收。

所以今天的关键词是“工作台资产清单”。以后每加一个入口、资料库、记忆、插件、MCP、云端 agent，都要先写清楚: 它能读什么，能写什么，要不要问我，出了问题怎么停，最后用什么证据证明完成。

### 今日结论

2026-08-16 的主线是: AI 工作流正在从“单个工具能做什么”进入“工作流合同能否被复用和验收”。OpenAI Developers 页面把桌面、硬件和云端协作放在同一个开发者叙事里；Codex CLI、Codex cloud、Responses API、Agents SDK、computer use、MCP 和 review rules 则继续把模型调用升级为可配置、可审计、可恢复的工程流程。

对个人工作流来说，今天最重要的不是追一个新按钮，而是把每次 AI 介入都写成小合同: 入口是什么，读写边界是什么，能否调用浏览器/终端/MCP，是否需要人工确认，失败如何停止，最后由哪个本地证据证明完成。Claude Code 的 hooks、GitHub Copilot coding agent 的 issue-to-PR 工作流、Obsidian 本地知识库项目，也都在验证同一个方向: agent 越多，越需要前置权限、后置验收和可回放的过程记录。

对 AI Radar 的直接动作是: 后续日报自动化应新增“工作流合同模板”和“只读采集证据等级”。一级证据是官方文档或 changelog；二级证据是高质量作者长文或公开项目；三级证据只能作为灵感，不进入 Top 5。每条可复用知识卡片都要能落到一个清单、脚本、规则或人工验收动作。

### Codex/GPT 工作流启发

1. 开发者入口正在合并，责任不能合并

OpenAI Developers 把 API、Codex、Agents 和开发者资源放在同一入口，降低了启动成本。但入口合并不代表职责合并: Chat 负责判断，Codex/CLI 负责本地执行，API/Agents 负责程序化工作流，本地 Git 和部署证据负责最终验收。

2. Codex CLI 是本地证据链核心

CLI 的价值不只是“会改代码”，而是能把仓库规则、权限、skills、MCP、review、终端命令和 Git 差异放在同一条链路里。日报自动化也应该继续坚持本地文件和命令作为完成证据。

3. Responses API 是统一循环，不是万能通道

Responses API 适合统一多轮状态、工具调用、MCP、computer use 和后台任务；但它同时要求清楚处理 state、工具权限、数据保留、轮询终态和失败恢复。没有这些合同，background run 只会放大不可见风险。

4. Computer use 默认需要隔离

任何浏览器/桌面自动化都要把页面内容当成不可信输入。只读采集优先公开网页；确需 UI 时必须按“观察前态 -> 声明动作 -> 执行动作 -> 回传新状态 -> 验收或停止”的证据环运行。

5. MCP 和 plugins 要先做白名单

MCP server 或 plugin 看起来像“多了一个工具”，实际可能带入账号权限、外部写入和网络访问。日报场景只需要公开只读采集；任何新连接器进入前，都要列出能读什么、能写什么、凭证在哪里、如何禁用。

6. Review rules 是内容发布合同

Custom Code Review rules 的思路可以直接迁移到内容自动化: 日期必须当天、source card 字段必须齐、signals 至少 8 条、knowledge 至少 3 条、report-data 必须和 JSON 同步、公开边界不能漏。

7. Claude Code hooks 提供前后置闸门样板

hooks 的价值是把“执行前检查”和“执行后验证”变成可重复机制。Codex 本地自动化也可以把写入前的路径检查、写入后的 JSONL/secret/local-path 扫描固定下来。

8. GitHub coding agent 适合 issue-to-PR，不适合无合同写入

GitHub agentic workflows 把 issue、branch、safe outputs 和 review 串起来，适合工程任务队列。个人自动化可借鉴它的 work item 思维，但最终仍要检查 diff 和部署状态。

9. Obsidian second brain 要分清资料层和行动层

Claudian 这类项目说明本地知识库可以成为 agent 工作面的一部分，但 vault 读写要先在备份库试验。公开日报只能使用公开来源和总结后的知识卡片。

10. 今日最好沉淀的是“合同”，不是“工具清单”

工具每天会变，但合同稳定: 目标、入口、边界、权限、证据、停止条件、回滚方式。后续 AI Radar 可以用合同模板筛选哪些玩法值得长期复用。

### 可沉淀知识卡片

#### 卡片 1: 工作流合同模板

- 概念: 每次让 AI 接手任务前，先写清入口、边界、权限、交付物、验证命令和停止条件。
- 适用场景: Codex 自动化、Workspace Agent API、Responses background mode、GitHub coding agent、Claude Code hooks。
- 操作步骤: 写目标 -> 写入口 -> 写读写边界 -> 写工具权限 -> 写交付物 -> 写验证证据 -> 写停止/回滚。
- 风险: 没有合同的 agent run 很容易把“已启动”误报成“已完成”。
- 原文: https://developers.openai.com/codex/cli

#### 卡片 2: 只读采集证据等级

- 概念: 把来源分成一级官方文档/changelog、二级高质量长文/公开项目、三级社区灵感。
- 适用场景: AI Radar、趋势日报、竞品扫描、X/网页混合采集。
- 操作步骤: 先找官方原文 -> 再找高质量解释 -> 最后用社区项目补玩法 -> 每条标 confidence -> Top 5 只放可复核来源。
- 风险: 社区转述可能更热，但缺少原文时不能作为核心证据。
- 原文: https://help.openai.com/en/articles/6825453-chatgpt-release-notes

#### 卡片 3: Hook 式前后置闸门

- 概念: 把执行前检查和执行后验证固定下来，让 agent 行为可重复、可拦截、可复盘。
- 适用场景: 文件写入、代码修改、日报发布、浏览器自动化、MCP 工具调用。
- 操作步骤: 执行前检查路径/权限/目标 -> 执行动作 -> 执行后跑测试/扫描/同步检查 -> 失败时停止并记录。
- 风险: hook 不能替代权限边界；它只是更早暴露风险。
- 原文: https://docs.anthropic.com/en/docs/claude-code/hooks

#### 卡片 4: 本地知识库沙盒

- 概念: Obsidian 或本地 vault 接入 coding agents 前，先用可丢弃或备份库建立沙盒。
- 适用场景: second brain、日报资料库、写作素材、长期项目记忆。
- 操作步骤: 复制小样本 vault -> 只读试跑 -> 开启 diff 预览 -> 限定写入目录 -> 验证 provider/MCP/权限 -> 再考虑主库。
- 风险: 知识库包含隐私和长期记忆，不能直接暴露给未审计工具。
- 原文: https://github.com/YishenTu/claudian

## 白话版

今天这期像是在给“AI 施工队”写施工合同。

以前我们容易盯着工具本身: 这个按钮会不会写代码？那个 agent 会不会上网？现在更关键的是: 谁从哪个门进来，能拿哪把钥匙，能不能碰仓库，施工完谁验收，出错从哪里停。

OpenAI Developers 像总服务台，把 Codex、API、Agents、桌面和云端入口都摆在一起。Codex CLI 像本地施工队，Responses API 像统一派工系统，computer use 像让 AI 去看屏幕和点按钮，MCP/plugin 像外接工具箱，review rules 像验收表。Claude Code 的 hooks 则像门口和出口各放一个检查员: 进去前看钥匙对不对，出来后看活儿有没有过检。

所以今天不建议再单纯追“又出了什么新工具”。更值得做的是一张合同表: 目标是什么，入口是谁，能读什么，能写什么，什么动作要问人，失败怎么停，最后看哪个证据算完工。

iPhone 还是对讲机，负责派工和问进度；Mac/Codex 还是施工现场和质检台，负责真正写文件、跑检查、提交、部署。资料库像档案柜，可以帮你找材料，但不能替你签验收单。
